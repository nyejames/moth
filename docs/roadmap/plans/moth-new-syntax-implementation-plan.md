## Mandate for the implementing agent

Read [Unified Bracket Construction for Moth](../../unified-bracket-construction-design.md) and [Moth Surface Syntax After Unified Bracket Construction](../../moth-surface-syntax-design.md) **in full before implementing**. In this plan, B and S refer to the numbered sections of those documents. Their examples and acceptance tables define the destination. The older revision links in the designs explain the starting point. Consult the two checked-in files even if the originals are unavailable.

Ship one Moth grammar and the corresponding MON data grammar. At the end of this migration Moth code has **no semicolon or fat arrow**. The subsequent constrained-closure work introduces `=>` for closure expressions. This includes closing blocks, choice definitions, match arms, readiness arms, inline exceptions and feature-gated source. Keep the return-type arrow, choice qualification, the two channel operators and range spellings. Quoted data, raw template bodies, comments and embedded languages retain their bytes. A malformed program receives the ordinary current-grammar error at its source. Add no migration messages, aliases, deprecated tokens, automatic fixes for old spellings, version switches or legacy parser. Historical examples in these two design records are evidence.

Use this branch and PR throughout. Commit tested, coherent changes at stable points. The order below separates reusable compiler work from the single change that assigns new meanings to source tokens. Phases 1-3 can land independently only where an existing caller exercises the change with today's grammar. Keep new-only wiring with its consumer in phase 4. Phase 4 is one public changeover across Moth, MON, fixtures and docs. Prepare its work packages in parallel against a shared revision, integrate them in the worktree and publish the green result. Never require an earlier commit to a broken intermediate dialect or a second parser just to divide the work.

Leave fewer independent owners of the same fact, delete dead production paths and keep the simple literal path cheap. Compare comparable workloads and production line counts separately from expanded tests, generated output and audit records. Retain a small specialised path when it is easier to verify or measurably cheaper. Preserve or improve meaningful coverage even when improvements add code.

## How to run each phase

1. Record the actual revision and validation state in working notes. Read `AGENTS.md`, the routed canonical references and both sides of each changed handoff. Check the progress matrix, active work, open findings and bug queue. Identify the current owner, callers, obsolete paths, public examples and case IDs. Record a pre-change observation for each contract the phase changes or must preserve.
2. Implement the phase on the integration branch. Keep each grammar decision at one owner. Change the owner, its callers, fixtures and executable examples together. Track each affected source family by path or case ID, intended meaning, replacement or intentional retained use and verification. Keep deliberate old-form negatives separate from fixtures that must still reach a later-stage failure.
3. Run the phase's focused checks below. Give the audit coordinator the resulting revision, changed surfaces, producer and consumer boundaries, actual commands, results and limitations. Map the work to named areas in `docs/roadmap/audit-log.md`, adding a bounded owner area when necessary. A phase spanning several areas needs enough runs to cover them all.

### Independent audits and closure

Run every kind in `docs/roadmap/audit-kinds/` at the end of **every phase**. Dispatch subagents in waves if needed. Each assignment covers one kind and one concrete area. Follow `docs/roadmap/audit-guide.md`, the kind's checklist and `docs/roadmap/audits/README.md`.

|---|---|

| Performance | Inspect repeated work, retention and fast paths. Attribute measured differences to comparable inputs and configuration. |

| Comments | Check module purpose, cross-stage invariants, order and failure explanations. Remove stale or noisy commentary. |
| Documentation | Verify canonical rules, status, teaching examples, links and rendered behavior against their owners. Read noncompiled examples separately. |

The coordinator serializes reservations and shared index updates. Before inspection, reserve one unused `AUD-####` across both audit folders for each formal run, create its skeleton in `open_audits/` and register it under `Audits in progress`. Auditors inspect and write evidence. Record actual boundaries inspected, baseline, checked-clean paths and limitations. For each finding give the violated contract or cost, evidence, strongest counter-explanation, root owner and verification. Triage after the report. Assign a separate implementation task for every valid finding. Fix the owner, delete the displaced path and add or strengthen the regression that proves the correction. Close every validated finding in the touched areas. Log an unrelated incidental lead in the repository's bug queue with its evidence and owner. A tracker entry cannot satisfy this gate.

A verifier other than the fixer repeats the repro or checks the invariant, inspects consumers, confirms the superseded path is gone and reruns invalidated checks. Re-audit materially changed evidence. Cover all remaining phase surfaces after a partial run. Record why rejected candidates are disproved and link superseded duplicates to their verified resolution. Remove resolved bug entries in their fix commits. When all formal findings are resolved, archive the report in `closed_audits/`, clear its open-index entries, update navigation and record its closeout in `completed_audits_log.md`. Archive clean runs too. Advance only with all eight kinds accounted for, zero valid open findings and the separate `AGENTS.md` Slice review complete.

### 4A. Capture delimiters and declarations once

1. Change the token shapes and source modes in `src/compiler_frontend/tokenizer/{schema,lexer,text_modes}.rs`. Keep every structural token on its original byte span. A bracket head switches to body-text mode at its own colon. A nested call, bracket, `::`, quoted string or embedded body owns its own punctuation. Test both directions of nesting. In an arm guard a template colon belongs to the bracket. In a bracket head containing a braced `if n is { ... }`, a `case 0:` colon stays in code mode through the matching block closer. If that expression position rejects a producing block, assert its ordinary position error. In `[:case Ready: {ok};]` all body punctuation is literal String data. Retire the source semicolon closer and the arm-only fat arrow. Retain function and Route arrows.
2. Change `headers/top_level_classifier.rs`, `headers/header_dispatch.rs` and `declaration_syntax/{declaration_shell,choice}.rs` together. After a declaration name and any generic parameters, distinguish `= |` for structs, `= {` for choices and an ordinary binding initializer. This deliberately overlaps the former untyped brace collection. Only declaration position claims a choice. Retain `Choice::Variant` as qualification. Parse the comma-separated alternatives through `parse_choice_shell` and retain the existing field-list parser. A one-variant choice still exposes its variant name. Standalone braces have no expression or anonymous-block production.
3. Capture braced function, const-function, receiver-method, trait and control bodies with their opener and half-open token range. Rework `capture_function_body_range_from_cursor`, `headers/trait_headers.rs`, `utilities/token_scan.rs` and `tokenizer/line_scanning.rs`. Delete the pending colon and match-depth rules that prevent an arm from accidentally opening a region. Keep the innermost opener for EOF diagnostics and retain each actual branch boundary. In `headers/file_parser.rs::parse_headers_in_file_inner`, replace the independent colon/semicolon block count. An entry bracket inside a conditional stays in that conditional. Only a true top-level bracket reaches `handle_direct_template_item` or `handle_runtime_template_item`. Check `template_control_flow_top_level_runtime_fragment_order` and `top_level_fragment_mixed_const_runtime_order` for ordered output.
4. In `declaration_syntax/type_syntax/parse.rs::parse_collection_type`, recognize `[T]`, `[N T]` and `[K = V]` in type position, including nested types and the existing postfixes. Preserve coverage checking, guard fallthrough, capture aliases and bodyless final fallback in statement matches. Replace the separator searches in `ast/statements/match_arm_boundaries.rs`, the qualified-arm lookahead in `headers/top_level_classifier.rs` and the raw-character signed-arm scan rooted at `tokenizer/lexer.rs::line_initial_match_arm_header`.
