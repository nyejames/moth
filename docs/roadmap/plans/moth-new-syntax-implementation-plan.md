## Mandate for the implementing agent

Read [Unified Bracket Construction for Moth](../../unified-bracket-construction-design.md) and [Moth Surface Syntax After Unified Bracket Construction](../../moth-surface-syntax-design.md) **in full before implementing**. In this plan, B and S refer to the numbered sections of those documents. Their examples and acceptance tables define the destination. The older revision links in the designs explain the starting point. Consult the two checked-in files even if the originals are unavailable.

Ship one Moth grammar and the corresponding MON data grammar. At the end of this migration Moth code has **no semicolon or fat arrow**. This applies to closing blocks, choice definitions, match arms, readiness arms, inline exceptions and feature-gated source. Closures V1 introduces `=>` solely for closure expressions after this plan is complete. Keep the return-type arrow, choice qualification, the two channel operators and range spellings. Quoted data, raw template bodies, comments and embedded languages retain their bytes. A malformed program receives the ordinary current-grammar error at its source. Add no migration messages, aliases, deprecated tokens, automatic fixes for old spellings, version switches or legacy parser. Historical examples in these two design records are evidence.

Use this branch and PR throughout. Commit tested, coherent changes at stable points. The order below separates reusable compiler work from the single change that assigns new meanings to source tokens. Phases 1-3 can land independently only where an existing caller exercises the change with today's grammar. Land code that only serves the new grammar with its consumer in phase 4. Phase 4 is one public changeover across Moth, MON, fixtures and docs. Prepare its work packages in parallel against a shared revision, integrate them in the worktree and publish the green result. Never require an earlier commit to a broken intermediate dialect or a second parser just to divide the work.

Leave fewer independent owners of the same fact, delete dead production paths and keep the simple literal path cheap. Compare comparable workloads and production line counts separately from expanded tests, generated output and audit records. Retain a small specialised path when it is easier to verify or measurably cheaper. Preserve or improve meaningful coverage even when improvements add code.

## How to run each phase

1. Record the actual revision and validation state in working notes. Read `AGENTS.md`, the routed canonical references and both sides of each changed handoff. Check the progress matrix, active work, open findings and bug queue. Identify the current owner, callers, obsolete paths, public examples and case IDs. Record a pre-change observation for each contract the phase changes or must preserve.
2. Implement the phase on the integration branch. Keep each grammar decision at one owner. Change the owner, its callers, fixtures and executable examples together. Track each affected source family by path or case ID, intended meaning, replacement or intentional retained use and verification. Keep deliberate old-form negatives separate from fixtures that must still reach a later-stage failure.
3. Run the phase's focused checks below. Give the audit coordinator the resulting revision, changed surfaces, producer and consumer boundaries, actual commands, results and limitations. Map the work to named areas in `docs/roadmap/audit-log.md`, adding a bounded owner area when necessary. A phase spanning several areas needs enough runs to cover them all.

### Independent audits and closure

Run every kind in `docs/roadmap/audit-kinds/` at the end of **every phase**. Dispatch subagents in waves if needed. Each assignment covers one kind and one concrete area. Follow `docs/roadmap/audit-guide.md`, the kind's checklist and `docs/roadmap/audits/README.md`.

| Kind | What the reviewer must establish |
|---|---|
| Correctness | Trace an accepted input and its nearest rejection through the owner and consumers. Check result, order, scope, identity, failure and publication. |
| Diagnostics | Inspect stable code, reason, primary and related source, recovery and cascades. Retired forms receive ordinary current-grammar errors. |
| Performance | Inspect repeated work, retention and fast paths. Attribute measured differences to comparable inputs and configuration. |
| Redundancy | Trace each shared fact to its owner. Find obsolete grammar, adapters, duplicated interpretation and surviving replacement paths. |
| Tests | Check real assertions and selected targets against each contract. Identify a realistic wrong outcome an assertion would catch or miss. |
| Style | Review actual callers, data flow, naming and module boundaries for concrete maintenance costs. |
| Comments | Check module purpose, cross-stage invariants, order and failure explanations. Remove stale or noisy commentary. |
| Documentation | Verify canonical rules, status, teaching examples, links and rendered behavior against their owners. Read noncompiled examples separately. |

The coordinator serializes reservations and shared index updates. Before inspection, reserve one unused `AUD-####` across both audit folders for each formal run, create its skeleton in `open_audits/` and register it under `Audits in progress`. Correctness uses `docs/bug-reports.md` and a `Correctness YYYY-MM @<revision>` coverage entry. It has no formal report or ID. Each other kind records its report ID in the area's coverage row and links unresolved findings from `open-audit-findings.md`.

Auditors inspect and write evidence. Record actual boundaries inspected, baseline, checked-clean paths and limitations. For each finding give the violated contract or cost, evidence, strongest counter-explanation, root owner and verification. Triage after the report. Assign a separate implementation task for every valid finding. Fix the owner, delete the displaced path and add or strengthen the regression that proves the correction. Close every validated finding in the touched areas. Log an unrelated incidental lead in the repository's bug queue with its evidence and owner. A tracker entry cannot satisfy this gate.

A verifier other than the fixer repeats the repro or checks the invariant, inspects consumers, confirms the superseded path is gone and reruns invalidated checks. Re-audit materially changed evidence. Cover all remaining phase surfaces after a partial run. Record why rejected candidates are disproved and link superseded duplicates to their verified resolution. Remove resolved bug entries in their fix commits. When all formal findings are resolved, archive the report in `closed_audits/`, clear its open-index entries, update navigation and record its closeout in `completed_audits_log.md`. Archive clean runs too. Advance only with all eight kinds accounted for, zero valid open findings and the separate `AGENTS.md` Slice review complete.

3. Keep unary negative literals distinct from subtraction and preserve legitimate newline-leading `is`.
4. Preserve the original diagnostic subject and opener spans through nesting, malformed input, end of file and module boundaries. Stress misnested delimiters, a damaged first arm followed by a valid arm, logical-line continuation and comments/Unicode before a failure. Use the normal diagnosed-user lane and bound recovery work on deeply malformed input.

**Close phase 1.** Check the old executable corpus still passes at this checkpoint. ### 4A. Capture delimiters and declarations once
