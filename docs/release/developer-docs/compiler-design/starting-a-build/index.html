Compiler design / 03. Starting a build

A build chooses its command, builder and folded project values before any page source enters the compiler.

A build starts before source compilation

moth build does not open @page.moth first. It asks a blunter question: which command, builder, profile and inputs should interpret this project at all?

Until those answers settle, the compiler has no honest graph to walk. Choose climate and soil first. Then grow the plant.

Command and capability surface

Bootstrap starts with the command, not with config.moth.

The command selects:

  • the active artefact builder (today the HTML builder arrives implicitly on the CLI)
  • the active build profile
  • tooling overlays such as check
  • explicit build inputs
  • target intent and command-specific options

The selected builder exposes a capability surface before config compilation:

  • project and entry config schemas
  • source-backed Core and Builder packages
  • binding-backed packages
  • style directives and external import providers
  • supported source file kinds
  • builder-provided primitive globals
  • target-affinity and capability metadata

Frontend-owned directives and compiler-owned builtins join that surface. A builder cannot replace them.

The command chooses what kind of project this build is allowed to be. That choice decides which source kinds, packages and targets the project may use.

The three commands also differ in how far they run:

  • build compiles the entry, package and provider union, then lowers and writes outputs when it succeeds.
  • dev compiles its complete graph on the first build. Rebuilds are currently fresh rather than incremental.
  • check casts the widest net, taking in every discovered module plus check-only orphans and package surfaces. It plans and validates all the way through the ValidatedMemoryPlan, then stops before lowering or writing anything.

Self-contained project config

config.moth is build-system-owned compile-time Moth source. It is not a module. It produces no HIR, no start, no runtime artefact and no package interface.

Config operates on exactly one authored file identity. It rejects source dependencies before path resolution. It never builds a config package graph.

The ordinary compiler owners still touch that one file:

tokenization
-> declaration-shell preparation
-> interface binding for the single config source
-> local declaration ordering
-> AST semantic checking and folding
-> folded config values

Then config stops. No borrow checker. No backend.

Allowed shape includes one required open project const record, private helper constants, builder and tooling section records, scalars, optional values, anonymous const records, collections of foldable values and templates represented by their folded strings.

Rejected shape includes dependency clauses, runtime declarations, functions, traits, page fragments, export: and nested config files.

A short shape for the walkthrough project might look like:

project #= |
    name = "compiler_walkthrough",
    entry_root = "src",
|

html #= |
    dev_output = "dev",
    release_output = "release",
|

config.moth does not select the builder. The command already did.

Config runs through one named compiler service, not a build-owned copy of the frontend. The build system hands over the single authored source and receives folded values, authored key locations and diagnostics. Config schema and how folded values apply to the project record stay build-owned.

Build configuration values and @project

A direct field of project may declare a build-config contract with #Config of T, meaning the command line can override it. Two conditions gate that, and both must hold: the selected project schema marks the field Configurable, and its value has a supported primitive or optional primitive shape.

Registered identity, source-discovery and compiler-control fields are fixed-only and reject the qualifier outright. The qualifier itself is compiler-owned, and the semantic type stays plain T. Accepted types stay deliberately narrow: String, Int, Float, Bool, Char and optional forms of those.

Command and programmatic inputs become concrete primitives immediately, before source contracts are checked:

  • exact true and false become Bool
  • complete whole numbers become Int
  • decimal or exponent forms become Float
  • quoted characters become Char
  • quoted strings become String
  • every remaining valid unquoted value falls back to String, including empty text after name=

Quoting forces ambiguous text such as "true" to stay a String. A value that opens with a quote must close as a complete valid literal, and a malformed one is a command-input diagnostic rather than a silent fall back to String. Omit an input and optional absence resolves to none.

Resolution order for a direct project #Config:

  1. explicit CLI or programmatic build input
  2. builder-provided primitive global
  3. the folded declaration default
  4. a structured missing-input diagnostic

A source contract resolves against a longer chain, because the project gets first say:

  1. a compatible fixed direct project field
  2. a resolved direct project #Config
  3. source-only CLI or programmatic input
  4. builder-provided global
  5. the shared source default
  6. a structured missing-input diagnostic

The folded project record becomes a specialised immutable ProjectGlobalsInterface under the reserved @project dependency root.

That interface carries stable field identities, folded backend-neutral values, source locations, field-level fingerprints and project-context provenance. It carries no AST, no HIR and no runtime body.

Normal modules may bind @project explicitly. Nothing injects it silently. Child modules, dependency aliases and packages cannot steal the @project root. Direct re-export of @project is forbidden.

For the greeting walkthrough, record the values Stage 0 needs for entry discovery: project name, entry root and builder sections. Those folded facts bridge files on disk to a project the graph can name.

Resolved source #Config values become ordinary folded constants. They use ordinary if for static Bool specialisation. Moth has no #Config if and no config-specific HIR node.

The ownership boundary

Draw the line early and keep it sharp.

Owner

Responsibility

Build system

discovers source, builds graphs, schedules modules, plans entries, writes outputs

Compiler

prepares syntax, binds interfaces, checks semantics, lowers HIR, validates access and target contracts over explicit inputs

Builder

assembles successful artefacts into project-shaped outputs after compilation succeeds and maps stable source semantics to platform-specific artefacts

The compiler does not wander the filesystem inventing a project. The builder does not re-parse @page.moth to rediscover greet. Each stage trusts the previous owner's facts.

The command and build system own target intent, target partition and physical-variant orchestration. Compiler-owned validation checks the assignment it is handed rather than choosing it. Builders expose stable capabilities and map them to target artefact forms. Source never observes physical target identity at all.

What can fail here

  • unknown command or unsupported builder capability
  • invalid config shape, forbidden config dependency or missing required input
  • entry-local config: syntax, which remains deferred under its own implementation plan

When the walkthrough mentions entry-local config, label current versus accepted because that surface remains deferred.

Why Moth does it this way

Alternative: an unrestricted host-language build script that can do anything the host process can do.

Choice: command-selected capabilities and typed compile-time config.

Benefit: the project contract stays visible and bounded before discovery. Tools can validate schema without executing arbitrary host code.

Cost: users lose general host-code build hooks and must fit builder schemas.

Roadmap and current status

  • Accepted design: one self-contained config.moth and a specialised ProjectGlobalsInterface.
  • Current implementation: grouped config.moth, direct and source #Config, typed --input for build, check and dev, ordinary static-if integration and immutable explicit @project.
  • Queued work: entry-local config: blocks, under entry-config-blocks-runtime-title-plan.md.
  • Deferred or outside scope: config dependencies and a general Moth build script system.
