Compiler design / 03. Starting a build

A build chooses its command, builder and folded project values before any page source enters the compiler.

A build starts before source compilation

moth build does not open @page.moth first. It asks a blunter question: which command, builder, profile and inputs should interpret this project at all?

Until those answers settle, the compiler has no honest graph to walk. Choose climate and soil first. Then grow the plant.

The Alpha compiler currently uses grouped project/html records, direct and source #Config of T contracts and reserved page_* metadata. The $config, $project and $html_builder forms in this article are accepted queued design, not current syntax.

Command and capability surface

Bootstrap starts with the command, not with config.moth.

The command selects:

  • the active artefact builder (today the HTML builder arrives implicitly on the CLI)
  • the active build profile
  • tooling overlays such as check
  • explicit build inputs
  • target intent and command-specific options

The selected builder exposes a capability surface before config compilation:

  • owned compiler and builder directive signatures, with config-only contexts
  • source-backed Core and Builder packages
  • binding-backed packages
  • style directives and external import providers
  • supported source file kinds
  • builder-provided primitive globals
  • target-affinity and capability metadata

Frontend-owned directives and compiler-owned builtins join that surface. A builder cannot replace them. Unknown directives error and known-but-unavailable forms receive a deferred-feature diagnostic; there is no inactive-builder ignore policy. Multi-builder projects wait for future structural $feature selection.

The command chooses what kind of project this build is allowed to be. That choice decides which source kinds, packages and targets the project may use.

The three commands also differ in how far they run:

  • build compiles the entry, package and provider union, then lowers and writes outputs when it succeeds.
  • dev compiles its complete graph on the first build. Rebuilds are currently fresh rather than incremental.
  • check casts the widest net, taking in every discovered module plus check-only orphans and package surfaces. It plans and validates all the way through the ValidatedMemoryPlan, then stops before lowering or writing anything.

Self-contained project config

config.moth is build-system-owned compile-time Moth source. It is not a module. It produces no HIR, no start, no runtime artefact and no package interface.

Config operates on exactly one authored file identity. It rejects source dependencies before path resolution. It never builds a config package graph.

The ordinary compiler owners still touch that one file:

tokenization
-> declaration-shell preparation with retained directive and input-contract facts
-> interface binding for the single config source
-> local declaration ordering
-> AST semantic checking and folding
-> validated directive arguments, folded project and builder settings, and bootstrap input results

Then config stops. No borrow checker. No backend.

The accepted shape contains explicit $config declarations, exactly one $project invocation and, for an authored HTML project, exactly one $html_builder invocation. It may also contain private helper constants, scalars and other foldable values allowed by the single-file compile-time surface. Bare $html_builder supplies its defaults.

Rejected shape includes dependency clauses, runtime declarations, functions, traits, page fragments, export: and nested config files. Config does not select the builder; the command already did.

The accepted starter shape is:

$config
version #String = "0.1.0"

$project(
    name = "compiler_walkthrough",
    version = version,
    entry_root = "src",
)

$html_builder

The generated starter is queued with the implementation plan; moth new does not emit this form yet.

Config runs through one named compiler service, not a build-owned copy of the frontend. The build system hands over the single authored source and receives folded values, authored key locations and diagnostics. Config schema and how folded values apply to the project record stay build-owned. Source-module input defaults remain literal-only and resolve after graph discovery; that later resolution uses the canonical module service, not another evaluator.

Build configuration values and @project

Today’s Alpha implementation still accepts direct project fields and source declarations using #Config of T; that is current syntax, not the accepted provider model. The accepted replacement uses $config as a prefix on exactly one explicitly typed top-level # binding. Its name is the input name, its type is the contract and its initializer is the fallback value. $config is valid in config.moth and in specified selected-source declarations wherever an ordinary compile-time constant is legal.

Only explicit $config declarations create input contracts. A $project field named version is project metadata, not a version input provider. An ordinary version #String = "1.0" helper is not an input provider. @project publishes only the predefined project fields. A contract named version does not satisfy an omitted required $project version, and a project field named version does not satisfy a source input contract.

Ordinary constants still require initializers. A marked $config declaration may omit an initializer only for a required input; optional declarations resolve to none when no present fallback or external value exists. The accepted input types remain String, Int, Float, Bool, Char and one optional layer around those primitives.

Project identity, source discovery and compiler-control arguments remain fixed-only. $config dependence is rejected in $project's name, entry_root and template_const_loop_iteration_limit, including through helper constants. $project has strict predefined fields; it does not become an open metadata record.

Bootstrap contracts resolve in this order:

  1. explicit CLI or programmatic build input for that name
  2. a compatible builder-provided primitive global
  3. the declaration’s validated fallback or optional absence
  4. a structured required-input diagnostic

Selected-source contracts resolve in this order:

  1. the already-resolved matching bootstrap $config contract, after compatibility validation
  2. explicit input for a source-only contract
  3. a compatible builder-provided primitive global
  4. the common source fallback or optional absence
  5. a structured required-input diagnostic

The current typed --input name=value carrier remains shared by build, check and dev. Exact booleans, whole numbers, decimal or exponent forms, quoted characters and quoted strings receive their primitive types in that order; all remaining valid unquoted values fall back to String. Malformed quoted text is a command-input diagnostic, and there is no implicit numeric or String coercion. Programmatic input uses the same policy.

The folded $project result becomes a specialised immutable ProjectGlobalsInterface under the reserved @project dependency root. It carries stable field identities, folded backend-neutral values, source locations, field-level fingerprints and project-context provenance. It carries no AST, no HIR and no runtime body.

Normal modules may bind @project explicitly. Nothing injects it silently. Child modules, dependency aliases and packages cannot steal the @project root. Direct re-export of @project is forbidden.

For the greeting walkthrough, the bootstrap facts needed for Stage 0 are the project name, entry root and builder settings. The separate input-contract results travel alongside them; neither set is reconstructed by scanning @project.

Resolved source $config values become ordinary folded constants. They can feed ordinary if for static Bool specialisation after source discovery. Both branches remain frontend-valid, and ordinary static if cannot remove declarations or dependencies. Future compiler-owned $feature is a separate deferred structural-selection mechanism before graph and declaration publication, not another evaluator.

The ownership boundary

Draw the line early and keep it sharp.

Owner

Responsibility

Build system

discovers source, builds graphs, schedules modules, plans entries, writes outputs

Compiler

prepares syntax, binds interfaces, checks semantics, lowers HIR, validates access and target contracts over explicit inputs

Builder

assembles successful artefacts into project-shaped outputs after compilation succeeds and maps stable source semantics to platform-specific artefacts

The compiler does not wander the filesystem inventing a project. The builder does not re-parse @page.moth to rediscover greet. Each stage trusts the previous owner's facts.

The command and build system own target intent, target partition and physical-variant orchestration. Compiler-owned validation checks the assignment it is handed rather than choosing it. Builders expose stable capabilities and map them to target artefact forms. Source never observes physical target identity at all.

The compiler owns general directive syntax, $config contracts and $project semantics. The build system applies folded project settings and runs bootstrap and graph orchestration; the HTML builder owns $html_builder settings and $page root metadata.

What can fail here

  • unknown or unsupported directive, or a known directive in a config-only or root-invalid context
  • invalid config shape, forbidden config dependency or missing required input
  • strict $project field, required-version or configuration-dependence violation

The command and config service report these as structured diagnostics. Entry purpose and page selection are validated later by the build system; they are not recovered by reopening config.moth.

Why Moth does it this way

Alternative: an unrestricted host-language build script that can do anything the host process can do.

Choice: command-selected capabilities and typed compile-time config.

Benefit: the project contract stays visible and bounded before discovery. Tools can validate schema without executing arbitrary host code.

Cost: users lose general host-code build hooks and must fit builder schemas.

Roadmap and current status

  • Accepted design: one self-contained config.moth service with explicit $config contracts, strict $project and $html_builder invocations, separate bootstrap input results and a specialised ProjectGlobalsInterface.
  • Current implementation: grouped config.moth, direct and source #Config, typed --input for build, check and dev, ordinary static-if integration and immutable explicit @project.
  • Queued work: general-directives-and-project-config-plan.md for the directive/config cutover and html-page-directives-and-runtime-title-plan.md for root-only $page, page metadata and runtime title.
  • Deferred or outside scope: structural $feature selection, config dependencies and a general Moth build-script system.
