Compiler design / 12. Memory topology and lowering

Access validation and lifetime topology prove the legal program. The compiler-owned memory planner then chooses a physical representation for those validated facts, and backend lowering only encodes the resulting plan.

Static memory topology and backend representations

Moth separates two questions that often get bundled together:

  • Semantic legality: may the program access, retain and release these values?
  • Physical representation: which runtime storage and cleanup plan realises that legal program?

Borrow validation answers access questions. Lifetime-region and escape validation proves one legal lifetime topology. A memory-strategy planner then chooses a representation for each validated allocation family.

A garbage-collected representation can carry an already-proven topology, but garbage collection never supplies the proof. A capable full-control release backend must lower without a tracing or reachability collector.

The sentence to keep

Moth is reference-semantic by default, copy-explicit and move-inferred. It omits explicit reference types and lifetime syntax, not references themselves.

Moth keeps shared aliases and exclusive mutation in the language model without asking authors to write &T, &mut T or lifetime parameters. The compiler tracks those relationships and keeps source APIs small.

Two layers of memory safety

Access validation and lifetime validation work together, but they own different facts.

Borrow validation checks shared and exclusive access, alias activity, last potential use, optional affine transfer and reactive invalidation. It reads validated HIR and writes side tables.

Lifetime and retained-edge analysis checks one semantic lifetime owner, retained-edge outlives relationships, escapes, cycles, non-lexical intervals, cleanup frontiers, builder lifecycle roots and exported summaries.

Those two sentences carry five terms worth unpacking before the rest of the page leans on them.

Affine describes a cleanup responsibility exactly one owner holds at a time. It can pass to a new owner, but it never splits and never duplicates, so cleanup happens once at a proven final use. Borrowing a value doesn't take that responsibility. Transferring it does.

A retained edge is one value holding onto another so the second must outlive the first. A list keeping its items alive has retained edges. A local reading a value briefly does not.

A non-lexical interval is the stretch of control flow where something is genuinely still needed, which is usually shorter than the block it was declared in. The compiler picks the narrowest owner that works and widens only to the nearest enclosing owner on the same chain. It never slides sideways to an unrelated sibling scope or invents a broad owner to make the sums easier.

A cleanup frontier is a point where cleanup is provably safe. Reaching one takes a full proof: every relevant retained edge is gone, no live alias remains, nothing can recreate an edge and no external holder or surviving aggregate still retains it. Partial confidence does not count.

An epoch is one round of a fill-and-empty cycle. A collection repeatedly populated and cleared has many value epochs while the collection itself, and the memory backing it, outlives every one of them.

Neither analysis depends on a collector. A GC backend must receive the same validated topology as a collector-free backend.

The proof pipeline

The accepted memory pipeline reads from one owner at each stage:

access and copy rules
    -> borrow and last-use facts
    -> lifetime topology and retained-edge summaries
    -> complete intervals, frontiers and epochs
    -> backend-neutral memory requirements
    -> target-affinity analysis and partition
    -> target-contract validation
    -> per-physical-variant family/layout refinement
    -> target/profile-aware compiler-owned memory planning
    -> ValidatedMemoryPlan
    -> backend lowering

The seam worth memorising: backend-neutral memory requirements is the last shared artefact. Build-owned target partition and target-contract validation come next and establish the candidate physical variants. Only after that does work become per variant.

  • Shared topology is target-independent and profile-independent. It decides what the program means and whether it is legal.
  • Backend-neutral memory requirements are the last shared artefact: family identity, owners, intervals, frontiers, retention facts, REC candidacy, declared-region membership. They deliberately contain no selected strategy.
  • Target partition is build-owned. It assigns functions to targets and, with target-contract validation, creates a candidate physical variant.
  • Variant-specific physical planning is compiler-owned. Only here does the planner know the target, the build profile and the backend's memory capabilities, so only here can it choose stack or inline placement, affine cleanup, inferred-region allocation, declared-region bulk reclamation (which a physical arena may or may not represent), REC or a garbage-collected representation. The planner does more than select a strategy. Before lowering, it turns each semantic commit into one normalised per-family obligation transition, fuses same-family removals and additions and decides root-to-edge and edge-to-root reclassification.
  • ValidatedMemoryPlan is that decision, one per physical variant.
  • Lowering realises the plan and encodes those planned transitions. It never picks a strategy of its own.

The selection changes memory quality, not source legality or observable behaviour. Two variants of one source function may end up with different physical representations and identical semantics.

check runs through creation and validation of the ValidatedMemoryPlan and stops before lowering.

When transfer proof is missing

Moth infers cleanup-responsibility transfer only at a proven final use. If analysis cannot prove transfer on every relevant path, the operation remains a borrow and the statically proven region retains responsibility.

unproven transfer
    -> borrow remains
    -> statically proven region retains responsibility

This fallback keeps the source program under the same legal topology. It does not ask a capable release backend to switch to tracing garbage collection.

One fact, several consumers

One set of last-use and retained-edge facts feeds several decisions while each stage keeps its own responsibility:

Consumer

a shared or exclusive access may still be used

borrow conflict validation

Borrow validation supplies the facts. Lifetime analysis and memory planning own the decisions.

Explicit copies and declared regions

Existing values use shared access by default. copy place deep-copies the complete copyable graph, preserves its internal alias topology and shares no mutable allocation with the source. A non-copyable member, such as an external handle or resource, is a diagnostic rather than a silently surviving alias.

A copied acyclic graph may enter an inferred or declared destination region. A copied cyclic graph must enter one declared region as a whole, because declared regions are Moth's only source mechanism for direct cycles.

A declared region gives its own allocations one hard, count-free bulk lifetime. Last-use analysis still checks access within it, but it never releases a declared-region-owned allocation early, and region exit reclaims the domain together.

Count-free stops at the region boundary. An edge running from declared-region storage into an externally owned REC family stays a counted obligation, released at region exit before the bulk reclaim.

Backend representations

Backends realise the validated memory plan through different physical mechanisms:

  • Collector-free release: affine cleanup, inferred regions, declared regions and REC lower without tracing reachability.
  • Debug or GC-native representation: a collector may erase individual cleanup operations while preserving the same validated topology and source behaviour.
  • Retained Edge Counting: a narrow counted representation for persistent retained edges that disappear independently, covered below.
  • Physical coalescing: a planner may keep storage slightly longer to reduce overhead. Coalescing never widens semantic topology, changes an outlives relationship or changes diagnostics.

Retained Edge Counting

REC is a last resort, and the planner works down that ladder before reaching it. Selection needs all three conditions:

  1. runtime-many persistent retained edges that disappear independently
  2. no earlier mechanism answers precisely enough, meaning static cleanup, inferred regions, frontiers, declared regions, field splitting and cheap bounded retention have all been ruled out
  3. falling back to a region would hold substantial storage materially longer than the values are useful

A selected counter carries the live counted persistent-edge obligations plus at most one affine-root obligation.

REC counts only direct persistent edges in the post-refinement family graph. Transitive reachability never counts, which is exactly what keeps it away from tracing.

Contributing nothing at all:

  • ordinary aliases and parameters
  • temporary projections and get() results
  • read-only call borrows
  • statically known region-only edges
  • declared-region-owned targets

One storage operation may still contribute several direct edges, so counting is per edge rather than per statement.

REC is not general ARC, it is not source-visible retain/release behaviour and it never establishes legality.

Reclassification runs both ways and costs nothing at the counter. A final-use store turns the affine root into one persistent edge. A detached result turns one persistent edge back into an affine root. Either way that single reclassified edge produces zero net counter traffic.

An operation touching several direct edges at once still moves the count by whatever remains after those cancel out. And the planner fuses a same-family replacement, so the backend never emits a decrement to zero followed immediately by an increment for the same slot.

Backends consume a validated memory plan. They do not infer source meaning, reconstruct lifetime topology or choose a new strategy when lowering.

Reactive and builder-owned lifetimes

Reactive subscriptions and mounted fragments can keep state observable after the function that created it returns. Builder lifecycle roots such as page, mount, request, frame and arena domains enter the same lifetime proof as source regions.

A collector-free backend can use those lifecycle regions directly. A GC backend may represent the already-proven lifecycle with reachability, but reachability does not define which topology the compiler accepts.

What can fail

  • conflicting shared and exclusive access
  • a retained edge into shorter-lived storage
  • an escape from a declared or inferred region
  • an unproven or illegal cycle
  • missing boundary or lifecycle metadata
  • a missing physical strategy after successful topology validation

Source failures use structured diagnostics. Missing compiler-owned metadata or a missing physical strategy uses CompilerError.

Roadmap and current status

  • Accepted design: static borrow and lifetime proof, explicit copies, inferred transfer, declared regions, direct source-created cycles requiring one declared region, REC as a narrow physical strategy and collector-free release on capable backends.
  • Current implementation: shared and exclusive access checking plus much local future-use analysis is partial and working. Public provenance summaries are partial. The Wasm ownership projection is experimental and currently consumes borrow-checker advisory DropIfOwned sites directly, which is migration debt rather than the accepted input.
  • Queued work: consolidate and implement the collector-free memory and REC plans named in docs/roadmap/roadmap.md.
  • Deferred or outside scope: lifetime topology, retained-edge liveness and epochs, declared regions and cycles, memory-strategy planning, REC, field splitting, region lowering, builder lifecycle roots and collector-free verification.

Exit state

You leave with one model: static proof defines legality, the validated memory plan defines physical cleanup and a collector remains an optional representation for a topology already proven legal.
