Compiler errors as structured data

Suppose the page mistypes the dependency selection:

@greeting great

The failure is not "something went wrong." It is a precise event: an unknown dependency-bound symbol at a known location, in a known stage, with a stable code a tool can recognise.

Moth treats diagnostics as durable structured data. Rendering into English is a later, separate act.

The stage with the best context

Each stage owns the failures it is uniquely equipped to see.

Stage

unresolved provider, invalid root role, or a command-required entry missing

a declaration cycle inside one module

unsupported capability on a reachable function

A missing provider and a missing symbol look alike in a terminal and belong to different owners. Stage 0 resolves whether the provider exists at all. Stage 2 decides whether a name that provider publishes is visible here.

A single global "parser error" funnel would throw away context. The type checker already knows the expected type. The borrow checker already knows the place. Let the owner who holds the fact build its typed diagnostic draft.

Diagnostic data lanes

Three lanes matter.

User-facing diagnostics are typed DiagnosticDraft values. Producers create them through the owning family schemas, and DiagnosticBag accumulates them locally.

Owning boundaries capture typed facts and identity context, then freeze compact DiagnosticStore records and TypeDisplaySnapshot data into DiagnosticReports. Renderers read family facts through DiagnosticViews.

InfrastructureFailure carries operational failures: filesystem, tooling, provider, output and dev-server problems, plus internal failures whose impossibility is not yet proven. It holds a kind, stage, optional host path, message and typed details, never source spans or compact IDs. These mean "the build could not run," not "rename your variable."

Compiler bugs are proven-impossible states. compiler_bug! panics with a CompilerBugReport carrying the stage, Rust caller and invariant message; the host boundary renders it. A compiler bug is never a Result variant.

Compilation boundaries return CompilationResult<T>: Ok(CompilationOutcome::Success { value, warnings }), Ok(CompilationOutcome::Diagnosed(reports)) or Err(InfrastructureErrors). Warnings travel only with success; when infrastructure failures and diagnostics coexist, the infrastructure failure wins.

Stable diagnostic codes and typed family facts keep semantic identity separate from prose. Foreign-site references are report-owned frozen identity-context references indexed by ForeignSiteRecord. This storage change leaves diagnostic output unchanged.

Deferred-feature diagnostics stay distinct from outside-design-scope diagnostics. "Not implemented yet" and "not part of the language" are different sentences.

Semantic identities in messages

Type diagnostics begin with semantic TypeIds and context. Owning boundaries snapshot only the display facts needed for rendering into the report's TypeDisplaySnapshot; family views resolve them without retaining the module's full type environment.

Why wait?

Because the same identity might print differently in different tools, and because pretty names are not the semantic authority. Source spelling, canonical paths and human wording remain distinct layers. A stable code must not be repurposed for a different semantic family when someone rewrites a sentence.

Carrying and rendering

Stages accumulate typed drafts in local bags. Builds merge prepared facts in canonical order: file order and module order, never worker-completion order.

Rendering happens at CLI or tooling boundaries from frozen report views. The same typed event can feed a terminal, a future editor integration or a test harness.

Module outcomes split cleanly:

  • Success carries an artefact and may retain structured warnings
  • Diagnosed carries user diagnostics and no partial public interface
  • InfrastructureFailure aborts the owning project or package compilation because later results cannot be trusted

A consumer blocked by a diagnosed required interface never compiles as if the provider half-worked. A failed root does not feed its dependents. Independent graph branches may continue under build-system orchestration for check or tooling. A backend never receives a partial linkable project.

Parallel failures

Workers may finish in any order. Merge order ignores that race. Canonical module order and original source order decide how humans and tools see the list.

Per-stage articles still own their contracts. This page owns the transport and lane model, not a catalogue of every code.

What can fail here

  • user syntax, type, import, borrow or target failure
  • internal invariant, filesystem or backend failure

Exact wording in examples should track current constructors when you verify against the tree. Do not fossilise a poetic error string that the code never emits.

Why Moth does it this way

Alternative: construct final prose inside each parser or checker branch.

Choice: typed family drafts compacted into report-owned stores and rendered through read-only views.

Benefit: CLI, dev server and tooling render the same semantic event. Codes stay stable while wording improves.

Cost: family schemas, fact codecs and renderers become maintained data, not afterthoughts.

Roadmap and current status

  • Accepted design: separate diagnostic and error lanes plus deterministic rendering order.
  • Current implementation: producers and DiagnosticBag use DiagnosticDraft; boundary freezing builds compact typed stores and family views owned by ordered reports. Foreign-site context references are report-owned and indexed by ForeignSiteRecord; the diagnostic output model is unchanged.
  • Queued work: none for the completed compact diagnostic cutover.
  • Deferred or outside scope: this page does not catalogue every diagnostic code.
