Errors, options and assertions

Moth separates ordinary absence, recoverable failure and broken invariants. Many languages combine these cases through null values or exceptions, which hides part of a function's behaviour.

Use options for absence, implicit built-in failure for checked numeric work, typed Error! returns for explicit failure and assert only when continuing would violate an invariant. An enclosing catch or function contract delivers implicit failure. JS/HTML delivers private propagation, builtin Error materialisation and expression-wide catch; HTML-Wasm rejects recoverable numeric failure with a structured capability diagnostic. See Progress for per-target support.

Choose the explanation level: Error values

Error values

An Error carries a message and an unsigned numeric code.

missing = Error("Missing value")
coded = Error("Missing value", 200)

The code defaults to 0 and accepts 0 through 4294967295. A negative code is rejected, and an Int variable needs an explicit conversion.

Use the message to explain the failure. Use the code when a stable category is useful to callers or tools.

Code 0 does not mean success when a function returns the value as an error. Under the accepted contract, a bound catch for implicit numeric failure also receives Error. Typed errors keep their original message and code when caught.

The compiler and HTML-JS backend support this U32 contract. HTML-Wasm still rejects reachable Error values. See Progress for backend support.

Error carries Moth's builtin structured error type.

Its public fields:

  • message String
  • code U32 = 0
missing = Error("Missing value")
coded = Error(message = "Missing value", code = 200)
large = Error("Quota exceeded", code = 3_000_000_000)

Contract for error values

  • message carries the human-readable explanation.
  • code carries a stable unsigned code and defaults to 0.
  • Codes above the signed 32-bit maximum are ordinary valid values, up to the maximum of U32.
  • A negative code or a code above the maximum of U32 fails at the ordinary typed boundary. A negative literal is a compile-time diagnostic, and an Int variable needs an explicit fallible conversion.
  • code is a runtime error code, not a compiler diagnostic code.
  • Positional construction follows field order.
  • Named construction follows normal constructor argument rules.
  • Error is reserved by the language.
  • ErrorKind, ErrorLocation and StackFrame remain ordinary user-available names.

The compiler and HTML-JS backend preserve the U32 code through construction, propagation, recovery and host glue in every numeric profile. Reachable Error values remain target-rejected on HTML-Wasm until its aggregate/runtime support provides construction, propagation and field access. See Progress.

Error! in a function signature marks an error return channel. It does not create a panic path and it is not a separate ordinary value type.

Custom structs and other compatible types may also be used as explicit error slot types. Under the accepted implicit-failure contract, built-in Error! materialises escaping checked failure. A custom E! slot requires local recovery or explicit mapping instead.

A bound catch for implicit failure receives Error. When implicit failure and built-in Error! share a catch, an existing typed error keeps its message, code and identity rather than being replaced by a generic numeric failure. Returning Error with code 0 is still an error, not success. An unbound catch need not construct an observable Error for implicit failure.

Transparent aliases preserve Error's built-in identity. A wrapper or an unrelated custom type does not gain automatic conversion. See Catch and recovery for compatibility rules and Progress for current compiler support.

Casts between String and Error are documented by Casts.

Choose the explanation level: Error returns

Error returns

A function with an explicit typed error path adds one final return marked with !.

parse_number |text String| -> Int, Error!:
    if text is "":
        return! Error("Missing number")
    ;

    return 42
;

Normal return sends success values.

return! sends one error value.

The caller must handle that error by propagating it or catching it.

Checked numeric work has a separate implicit built-in failure path. Under the accepted contract, Error! materialises that failure for callers. A custom error slot needs local recovery or explicit mapping with catch and return!.

Private functions without an error slot may propagate implicit failure inside their module. Exported callables must declare Error! or handle that failure locally. See Progress for current compiler support.

A function with an explicit typed error path marks one return slot with !.

parse_number |text String| -> Int, Error!:
    if text is "":
        return! Error("Missing number", 200)
    ;

    return 42
;

Signature contract

  • A function may declare at most one error-channel slot.
  • The error slot must be the final return slot.
  • Success slots appear before it.
  • A function may have success slots plus one error slot.
  • A function may also expose only an error slot.
  • Success return slots contain types only. The error slot may carry a channel.

The error slot type is explicit. Error! is common, but a compatible custom error type can be used when the function contract requires it.

Returning an error

return! expression leaves through the current function's error channel.

  • The current function must declare an error slot.
  • Exactly one error value is required.
  • The value must be compatible with the declared error type.
  • return! is terminal for the current path.
  • Normal success values use return.

Error-only functions

A function may declare only an error slot:

validate |ready Bool| -> Error!:
    if not ready:
        return! Error("not ready")
    ;
;
  • The arrow is required: -> Error!.
  • No success return value is required.
  • Normal fallthrough is valid when no error is returned.
  • A nested block may use return! too. The statement leaves through the enclosing error-only function's error channel and terminates that path.
Failure = |
    message String,
|

fail |message String| -> Failure!:
    return! Failure(message)
;

Implicit failure at function boundaries

Checked numeric work produces implicit built-in failure. It neither wraps nor implicitly panics. The enclosing handler or function contract delivers that failure under the accepted rules:

  • A private function with no error slot infers and propagates it within the same module.
  • A built-in Error! slot materialises the corresponding Error when failure escapes local handling.
  • A custom E! slot requires local recovery or explicit mapping to E, even in a private function.
  • An exported callable with no error slot must discharge implicit failure. Any remaining possibility is a compiler diagnostic.

These rules apply to zero, one and multiple success returns. The public rule also covers receiver methods, generics and re-exports. A transparent alias of Error keeps its built-in identity; an unrelated wrapper does not. User-defined failure-conversion traits, error-conversion hooks and generic adapter searches are outside Moth's design scope, so mapping into a custom error stays explicit. Current compiler support remains documented by Progress.

Map implicit failure into a custom error with catch and return!:

GeometryError ::
    InvalidDimensions,
;

area |width Int, height Int| -> Int, GeometryError!:
    result = width * height catch:
        return! GeometryError::InvalidDimensions
    ;
    return result
;

Returning a custom error on one path does not discharge another escaping implicit failure. Failure in a handler contributes to the surrounding function's contract. Statically known invalid numeric work remains a compile-time diagnostic, including inside Error! functions.

First-class public Result values and result pattern matching are outside the language's error-channel path. Explicit typed errors require propagation with ! or recovery with catch. Implicit private propagation is documented by Error propagation.

Choose the explanation level: Error propagation

Error propagation

Add ! after a call with a typed error return when the current function should pass that error to its caller.

wrapper |text String| -> Int, Error!:
    value = parse_number(text)!
    return value
;

On success, value receives the parsed number.

On failure, wrapper returns the error immediately.

The surrounding function needs a compatible error return slot.

Implicit numeric failure follows a different accepted rule. A private function without an error slot propagates it to callers within the same module without postfix !. An Error! function turns escaping implicit failure into Error; an exported function without an error slot must recover locally. See Progress for current compiler support.

Postfix ! propagates a typed error through the enclosing function's compatible error slot.

wrapper |text String| -> Int, Error!:
    value = parse_number(text)!
    return value
;

Contract for error propagation

  • The handled expression must have a fallible error channel.
  • The enclosing function must declare an error slot.
  • The produced error type must be compatible with that slot.
  • On success, the expression yields its success values.
  • On failure, the current function returns the error immediately.
  • A no-success fallible operation may still use postfix ! as a statement.
  • Multi-success fallible calls may feed a matching multi-bind.
items ~{4 Int} = {}

~items.push(value)!

Postfix propagation is not panic syntax.

cast! uses the same outward error path for a fallible explicit cast, but its target and evidence rules remain owned by Casts.

Removed forms

Old inline fallback and bang-handler spellings are invalid.

-- INVALID: old inline fallback and bang-handler spellings
value = parse_number(text)!0
value = parse_number(text) err!

Use catch then ... or a block catch: handler for recovery.

Implicit private propagation

Checked numeric failure is compiler-owned control flow, not a first-class source-visible Error! expression. Under the accepted contract, private functions without an error slot infer and propagate it within the same semantic module. Their internal callers do not add postfix !.

product |left Int, right Int| -> Int:
    return left * right
;

export:
    checked_product |left Int, right Int| -> Int, Error!:
        return product(left, right)
    ;

    product_or_zero |left Int, right Int| -> Int:
        return product(left, right) catch then 0
    ;
;

checked_product materialises escaping implicit failure as a built-in Error. product_or_zero discharges it locally. An otherwise identical exported product without an error slot or recovery is rejected when multiplication may fail. Calling it with small values in one consumer does not repair its public contract.

A custom E! function must recover locally or map implicit failure explicitly with catch and return!. It receives no automatic conversion or hidden extra channel. Explicit typed errors still require ! or an applicable catch. See Error returns for the boundary rules and Progress for current compiler support.

Choose the explanation level: Catch and recovery

Catch and recovery

Use catch when the current code has a useful fallback.

count = parse_number(text) catch:
    then 0
;

Use catch |err|: when the message or code matters:

count = parse_number(text) catch |err|:
    io.line(err.message)
    then 0
;

A short fallback can stay on one line:

count = parse_number(text) catch then 0

Use then to provide the value expected by the surrounding assignment.

Recovering a complete expression

The accepted contract also lets catch handle checked numeric failure:

value = left * right + offset catch then 0
amount = load_amount(left * right) catch then 0

The first handler covers both operators. The second covers argument evaluation and the call when load_amount returns Error!. Parentheses around the whole protected expression are not required. See Progress for current compiler support.

Implicit failure and built-in Error! may share one handler. A bound err has type Error, and an existing typed error keeps its message, code and identity. A custom error cannot share that handler with implicit failure. Split the work or map it explicitly instead.

catch handles the complete selected expression locally, including implicit built-in failure and compatible typed errors.

The expression-wide rules below are delivered on JS/HTML. HTML-Wasm rejects recoverable numeric failure with a capability diagnostic. See Progress.

Protected expression

catch has lower precedence than the ordinary operators. Parentheses around the protected expression are not required.

value = left * right + offset catch:
    then 0
;

This handler covers multiplication and addition, not only the last operand. It also covers receiver evaluation, arguments, nested calls and cast operands.

amount = load_amount(left * right + offset) catch then 0

If load_amount returns Int, Error!, this handler covers its returned error and both arithmetic operations in its argument. Compatible typed calls inside the protected expression supply their success values without per-call !.

Evaluate the protected work once in ordinary source order. The first failure skips the rest of the expression and enters the handler, which replaces the whole expression's success values. Earlier successful mutations and IO remain visible. A catch is not a transaction, and failure in its handler goes outward rather than entering the same handler again.

Compatible failures

  • Implicit built-in failure alone is accepted. A bound name has type Error.
  • One or more built-in Error! outcomes may share a catch with implicit failure.
  • Existing typed Error values keep their message, code and identity, including code 0.
  • One custom error type E may share a catch when no implicit failure remains. The binding has type E.
  • A custom E! outcome mixed with implicit failure is rejected.
  • Two distinct typed error types are rejected, including custom E mixed with Error.

Split incompatible work into separate handled expressions or map errors explicitly. An unbound catch need not construct an observable Error for an implicit failure. A bound catch materialises the corresponding built-in error.

A checked operation, inferred-failure private call or typed error producer makes catch eligible. A literal or an ordinary infallible call alone does not. Later proof or optimisation removing the failure path does not invalidate an otherwise eligible catch. Statically known invalid numeric work remains a compile-time diagnostic, even inside a catch.

Block forms

Use catch: when the error value is not needed.

value = parse_number(text) catch:
    then 0
;

Use catch |err|: when the handler needs the error.

value = parse_number(text) catch |err|:
    io.line(err.message)
    then 0
;

The error binding:

  • is immutable
  • is visible only inside the handler
  • must not shadow another visible name
  • has the compatible error type described above

Inline forms

A simple recovery may stay on one logical line.

value = parse_number(text) catch then 0
label = load_label(text) catch |err| then err.message

Inline catch:

  • uses then
  • stays on one logical line
  • may produce the receiver's required value list
  • binds the error only inside the fallback expression
  • does not contain a statement body
  • cannot combine with postfix !

Value requirements

When the handled expression has success values and the receiving site needs them, every reachable handler path must:

  • produce the required values with then
  • leave the enclosing function with return
  • leave through its error channel with return!
  • end in a proven terminal assertion such as assert(false, "cannot recover")

A handler that can fall through without producing or terminating is invalid.

value = parse_number(text) catch |err|:
    io.line(err.message)
    return 0
;

A multi-success recovery uses then with the matching arity:

name, score = load_user(id) catch |err|:
    io.line(err.message)
    then "guest", 0.0
;

A fallible operation with no success values does not need then.

items ~{4 Int} = {}

~items.push(value) catch:
    io.line("push failed")
;

Context and conflicts

  • catch and postfix !, cast! or optional ? conflict on the same expression.
  • Explicit propagation still leaves the function. It does not target the nearest catch.
  • Catch bodies remain statement-like and are rejected inside conditions, templates and constants, except for directly foldable cast recovery at an explicit constant/default receiving boundary.
  • Comma, parenthesis, logical-line and statement boundaries still delimit the selected expression.
  • Grouping an operand without a catch inside it does not shrink an outer handler's scope.
  • First-class fallible carriers cannot be stored without handling.

A catch on an assignment's right-hand expression protects that expression only. Compound arithmetic and conversion back to the target are separate checks, and the target is written only after all checks succeed. To recover a complete compound update locally, catch a private helper call or compute and check the replacement before assignment. Catch-after-loop and grouped handlers are not part of this contract.

then and closed receiving sites are specified by Value-producing if.

Choose the explanation level: Options

Options

Use T? when a value may be missing and that absence is normal.

nickname String? = none

A normal String can be used where String? is expected.

Inspect a present value with is |name|:

display_name = if nickname is |name| then name else "guest"

Use postfix ? inside a function that also returns an optional value:

get_display_name |id String| -> String?:
    user = find_user(id)?
    return user.name
;

If find_user returns none, the current function returns none too.

T? is an optional value that may contain T or may be absent.

none is the only special absent value.

name String? = none
fallback String? = "guest"

Contextual wrapping

A value of T can be used where T? is expected.

none requires an immediate optional receiving context. It is not a standalone inferred type.

Optional values are not automatically unwrapped.

Present-value inspection

Inline inspection:

display_name = if maybe_name is |name| then name else "guest"

Block inspection:

display_name = if maybe_name is |name|:
    then name
else
    then "guest"
;

Statement inspection:

if maybe_name is none:
    io.line("missing")
;

Full option match:

label = if maybe_name is:
    "Priya" => then "Hi Priya"
    |name| => then name
    none => then "guest"
;

Option patterns support:

  • none
  • compatible literal present-value patterns
  • compatible relational present-value patterns
  • |name| to capture any present value
  • guards
  • else =>

An option match can be exhaustive without else => when it has both an unguarded none arm and an unguarded present-value capture.

Direct fallback syntax such as maybe_name else then "guest" is invalid.

Absence inspection

Statement if can test for absence:

if maybe_name is none:
    io.line("missing")
;

Equality and ordering

Options support equality comparisons:

present = maybe_name is "Priya"
absent = maybe_name is none
same = a is b

Two options can be compared only when they have the same option type and their inner type supports equality. Two absent values compare equal. Present values compare through the inner type's equality rule, and a present value never equals none.

Ordering operators such as < on optional values are not supported.

Postfix propagation

Postfix ? unwraps a present value or returns none from the enclosing function.

get_display_name |id String| -> String?:
    user = find_user(id)?
    return user.name
;

The exact contract is:

  • the operand must be optional
  • the enclosing function must have exactly one success return slot
  • that success slot must be a compatible optional type
  • the present payload becomes the expression result
  • absence returns none immediately
  • ? cannot be followed by catch

Options are compiler-owned value shapes. Source code does not construct public Option variants.

MON data boundary

Source optional rules above are unchanged. MON literal data documents the same explicit none by reference: optionality permits none, but only an explicit field default permits omission, so a missing optional field without a default is an error. Missing fields, explicit none and empty values stay distinct; defaults are prevalidated data applied only at the exact missing field, a supplied none is never replaced, and nested records are never deep-merged. That contract is Rust-only serialised-data documentation. See MON format.

Choose the explanation level: Assertions

Assertions

Use assert for a condition that must already be true.

assert(index < items.length())
assert(index < items.length(), "index must be in bounds")

The message is optional. When you add one it is an ordinary String? value, including a local string, runtime template snapshot or infallible string-producing call. It is still fully checked and normalized when the condition is the literal true. The message is normalized through the ordinary AST template path before it is discarded after final AST type/TIR validation, so its temporary AST-local TIR is removed with the message and no TIR reference, runtime handoff, reactive metadata, generated function or other runtime fact survives. Active messages are evaluated only on the failure edge. See Progress for current compiler and backend support.

Message construction must not escape through !, ?, return, break or continue, or through escaping implicit or typed failure. Handle fallible work before the assertion and pass an infallible message.

A false condition stops the current program path. Failure while computing the condition is not a false assertion result. It follows the enclosing failure contract instead.

Assertion failure is not a recoverable error and cannot be caught.

Assertions remain checked in development and release builds.

Use Error! for failures callers are expected to handle. Use assert for broken assumptions and impossible states.

assert provides an always-checked statement intrinsic for invariants.

The accepted end-state contract uses one required condition and one optional message:

assert |condition Bool, message String? = none|

This is compiler-owned metadata, not an importable or shadowable Moth function. The rules below describe the accepted contract. See Progress for current compiler and backend support.

assert(index < items.length())
assert(index < items.length(), "index must be in bounds")
assert(false, "unimplemented backend path")

Accepted forms

assert(ready)
assert(ready, "must be ready")
assert(condition = ready)
assert(ready, message = "must be ready")
assert(message = "must be ready", condition = ready)
assert(condition = ready, message = none)
  • The condition must resolve to Bool.
  • The condition is required.
  • The message resolves to String? and defaults to none.
  • A String promotes to String? through ordinary contextual coercion.
  • none selects the default failure text, "assertion failed".
  • A present message may be an ordinary infallible expression, including a local string, runtime template or infallible string-producing call.
  • Moth does not implicitly stringify other value types for an assertion message.
  • Named and positional arguments use the ordinary call rules. Positional arguments must come first, names must be condition or message, and a parameter cannot be supplied twice.
  • Mutable access markers are invalid for both parameters.
  • Parentheses are required.
  • The shared call-argument grammar owns trailing-comma behaviour.

The message is type checked, generic-inferred, evidence-checked and fully normalized, including nested templates, even when the condition is compile-time true. The normalized inactive message is then replaced with typed none before the AST/HIR boundary, so it publishes no TIR, runtime handoff, reactive metadata, generated-function request or downstream executable fact. An active message is evaluated only on the failure edge. A template-backed message is read as one snapshot at failure and does not create an assertion sink or live subscription. Message construction cannot escape its evaluation through !, ?, return, break or continue, or through escaping implicit or typed failure. This includes inferred failure from a private call without an error slot. Handle fallible message work before the assertion and pass its infallible value instead.

Failure behaviour

  • Assertions are checked in development and release builds.
  • Failure is unrecoverable in Moth source.
  • Failure does not produce Error!.
  • Postfix ! is invalid.
  • catch is invalid.
  • Expected runtime failures should use an implicit failure or typed error path instead.

The condition is evaluated normally. Implicit failure or a typed error while computing it is not a false Bool result and does not trigger assertion failure or message evaluation. That failure follows the enclosing handler or function contract. A typed error still requires its ordinary explicit handling.

Statement-only contract

assert:

  • cannot be assigned
  • cannot be passed as an argument
  • cannot be imported or aliased
  • cannot appear in template interpolation
  • does not produce a value

assert(false) and assert(false, "message") are statically terminal. assert(false, runtime_message) is also statically terminal after the failure-edge message is lowered.

They may end a function path that otherwise requires a value.

A dynamic assert(condition) is not statically terminal because the condition may succeed.

Runtime failures and termination

Checked operations and typed errors support recovery. Resource exhaustion and host termination remain outside that contract. Choose Advanced for the failure catalogue and the Wasm/JavaScript comparison.

Recoverable failure and termination

Moth separates a computation that cannot produce its normal result from an execution environment that can no longer support the program.

Checked numeric operations produce implicit built-in failure. Their enclosing handler or function contract delivers it, without wrapping or an implicit panic. Private functions with no error slot infer and propagate that failure within the same module, without postfix ! at each internal call. An explicit built-in Error! return channel materialises escaping failure as the corresponding Error. A custom error channel requires local recovery or explicit mapping. Exported callables expose their failures through a declared error channel or handle them before returning. The compiler diagnoses any implicit failure left unrepresented at that boundary.

Expression-wide catch handles the whole selected expression, including arithmetic, receivers, arguments and nested calls. Parentheses are not required. Implicit failures and built-in Error! outcomes may share one catch. The same rule applies to cast expression catch, so its handler may receive an arithmetic failure from the operand as well as a conversion error. A bound implicit-failure handler receives Error; an unbound handler need not construct an observable error value. Typed Error values keep their message, code and identity, including code 0.

One custom error type without implicit failure may share a catch. Custom errors mixed with implicit failure and two distinct typed error types are rejected. Split an expression or map its errors explicitly when its sources need different handling. Catch and recovery owns placement, boundary and explicit-propagation conflict rules.

The implicit start uses the built-in Error! rule and its generated caller reports an unsuccessful entry invocation. HTML publishes that invocation's runtime fragments only after success. Static HTML stays after failure. Release uses a generic safe notice, not the application error message as HTML. Entry runtime and fragments owns top-level propagation and entry delivery. docs/build-system-design.md > Development entry-error reports owns development presentation, host status and the rule that a runtime report does not poison global build success.

Handling an error does not undo earlier mutations or IO. Compile-time-known invalid numeric operations remain source diagnostics, including inside Error! functions and expressions followed by catch.

assert is the only way to author a deliberate panic. A failed assertion is unrecoverable in Moth and remains checked in release builds. catch handles Moth failure channels, not arbitrary JavaScript exceptions or Wasm traps.

An assertion's condition evaluates normally. Failure while computing it is not a false assertion result. The lazily evaluated message must not contain escaping implicit or typed failure, including inferred failure in a private call. Assertions owns the full condition and message contract.

Termination outside assert

The following cases remain outside the recoverable failure system. An infallible source operation promises no recoverable error result, not unlimited memory, stack space or execution time.

Allocation exhaustion or refusal by the runtime allocator

Recovery is not a language guarantee. Propagation, cleanup and reporting may themselves need resources. Growable push keeps its no-error-channel contract and traps on allocation exhaustion.

These are physical storage limits, not permission to wrap an address or corrupt memory. They remain fatal unless the particular API explicitly defines a recoverable limit error.

Recursion, deep call chains and calls into host code

Stack or host call-depth exhaustion

The host may stop execution before enough stack remains for normal Moth error propagation or cleanup. There is no recoverable stack-budget effect.

Foreign bindings, generated code or runtime internals

An unexpected host exception, invalid generated memory access or broken runtime invariant

A fault is not a declared API outcome. The host or tooling may report it, but Moth does not turn arbitrary faults into Error values or promise safe continuation.

The process, browser tab or embedding host

External termination, an execution limit or a host failure

The program cannot require an environment that has stopped executing it to run a handler. Even a final diagnostic is not guaranteed.

A full fixed-capacity collection is different from allocation exhaustion. Fixed push returns Error! when it has no free slot. Invalid collection indices and missing map keys also retain their documented typed error paths. Expected IO errors follow the called API's declared contract. Resource failure does not silently replace these ordinary errors.

Fatal resource handling still requires runtime checks that protect memory and storage invariants. Excluding recoverable allocation errors does not authorise unchecked address arithmetic or treating a refused allocation as valid storage. No assertion, fatal runtime fault or external termination guarantees rollback or completion of cleanup.

A Wasm trap ends the current invocation. It need not end the embedding process. In a JavaScript host it can surface as a WebAssembly.RuntimeError. Conversely, out-of-memory behaviour may include host termination rather than a catchable exception. Tooling that reports an unexpected startup fault is observing that fault, not adding a Moth recovery channel or proving a compiler bug. See the error-condition mappings and resource limits in the Wasm JavaScript embedding specification.

Checked operations and bare backend behaviour

The table compares Moth's required result with selected bare backend operations without Moth's semantic checks. It is not an unchecked Moth mode or a catalogue of exact generated instructions. Helpers and representations may differ. A backend must preserve Moth semantics wherever it supports the feature.

Arithmetic checks the promoted result domain, not an operand's storage width. For example, U8 + U8 yielding 256 is valid U32, not overflow. Narrowing that result back into U8 is a separate checked boundary. Moth / produces a binary floating-point result for integer operands, while // is integer division.

JavaScript's Number below means its binary64 primitive, not Moth's arbitrary-precision Dec family. A bare JavaScript Number operation does not enforce an I32 or U32 range. Bare BigInt operations have no fixed-width overflow limit, but still depend on host resources.

What checks and optimisations promise

A backend may remove a check when it proves that the failing case cannot occur. More expensive release analysis may remove more checks, but source acceptance, exported contracts and observable failure order stay the same. Programmer confidence is not an unchecked assumption available to the optimiser.

Handling a checked failure with assert(false, ...) makes termination explicit. It does not automatically remove the original check. Wasm integer addition wraps rather than traps, so panic-on-overflow still needs detection. Native-trap substitution for assertion handlers remains unsettled. Any accepted optimisation would need to preserve the full observable assertion contract, including required message work.

Grouped if: handlers, rewind or rollback, richer effects, explicit wrapping, other wrap-or-trap controls and native-trap assertion optimisation remain unsettled. This reference reserves no syntax or guarantee that they will be added. $checked is the separate borrow-proof budget, not a numeric mode. Recoverable resource exhaustion is outside Moth's design scope, not another pending failure effect.
