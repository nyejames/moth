PACKAGES AND BUILDERS PROGRESS

This page tracks current implementation status for Moth packages and project builders. It also records the important accepted gaps and next extensions for partial package surfaces so later work does not need to rediscover them from implementation details.

The compiler progress matrix tracks the core language, compiler, memory work and backend implementation. Backend implementation progress belongs there even when a project builder consumes that backend. This page tracks builder-owned project behaviour and the packages supplied by Core or a project builder.

Accepted deferred surfaces may appear here. Open design questions and outside-scope mechanisms do not. Package acquisition, resolver and package-manager sequencing remains roadmap work rather than something this matrix designs.

How to read and edit this page

  • Keep package rows focused on the implemented v1 surface and the most useful accepted next gaps.
  • Update a package row while working on that package so deferred extensions do not need to be rediscovered later.
  • Keep project-builder rows separate from backend implementation rows.
  • Put user-facing package and builder explanations in docs/src/docs/packages/** and the relevant project documentation.
  • Put implementation sequencing and unaccepted proposals in docs/roadmap/roadmap.md.
  • Use the status labels from this page's legend. Put backend-specific or deliberately deferred nuance in the notes column instead of inventing new status labels.

Status legend

Status Meaning
Supported Implemented for the current supported surface and expected to compile, type check and run through its advertised builder/runtime path.
Partial A useful subset is implemented, but important common operations, package surfaces or builder behaviour remain incomplete.
Experimental Present in the repository, but not part of the Alpha stability promise.
Deferred Accepted or design-compatible follow-up work that is not currently implemented.

Coverage legend

Coverage Meaning
Broad Multiple focused cases exist, including success and failure coverage.
Targeted Dedicated coverage exists, but not across all important edges.
Thin Coverage exists indirectly or through only a small number of cases.

Package model and infrastructure

Surface Status Coverage Runtime target Notes
Prelude policy Supported Targeted prelude symbol registration, namespace-alias plumbing and collision rejection coverage. Frontend / JS The builtin prelude policy registers io as a namespace alias to @core/io and leaves compiler-owned Error as a bare language symbol. Prelude is visibility policy, not a package origin or backing. There is no @core/prelude package.
Binding-backed platform packages Partial Broad package dependency, external constant, external signature, provider-created JS package, runtime asset/glue, Core package, prelude and backend validation coverage. Frontend / JS Rust-side and provider-created binding-backed packages expose free functions, opaque types and compile-time scalar constants. Project-local and builder-owned annotated .js files can create JS-backed package surfaces. Binding-backed packages do not expose receiver methods. Unsupported reachable calls for an active backend fail before lowering.
Source-backed package roots Partial Targeted AST-backed config loading, known-key and shape enforcement, self-contained config dependency rejection, generic package-root discovery, collision detection and public-surface enforcement coverage. Frontend / HTML Source-backed packages and regular modules share module-root and visibility rules. config.moth is compiled as one self-contained source before package discovery and rejects every dependency clause before path resolution.
Builder-provided source-backed packages Partial Targeted builder source-backed package root registration and HTML Builder package coverage. Frontend / HTML Builders expose source-backed packages through BuilderSurface.source_packages. The HTML builder provides @html as a source-backed package. Builder and project-local prefix collisions are hard config errors.
Project-local packages Partial Targeted structural support-package roots, rejected legacy package-folder configuration, independently registered builder packages, dependency resolution, generic normal module-root and public-surface coverage. Frontend / HTML Structural +*.moth support packages and the optional project-root facade define the accepted project-local package model. Legacy config-driven package_folders paths and the historical default lib/ are removed. Independently registered Builder/Core source packages retain their own package boundaries.
Builder runtime packages Partial Targeted built-in JS-backed package, runtime asset, runtime module, import-map, glue and backend validation coverage. HTML / JS Builder-owned runtime packages such as @web/canvas are binding-backed packages. They share the specialised external package registry and HTML external JS asset/glue pipeline with provider-created imports.
First-party no-third-party-dependencies guard Partial Targeted package-manager, vendored-root, allowed-runtime-import and rejected-module-import coverage. Validation / packages The first-party-deps validation owner inspects first-party implementation roots plus the compiler-owned JavaScript inventory. Physical .js assets, Core helper bodies, inline lowering templates and registered runtime modules are checked. User-owned and future dependency packages, generated glue, documentation, tests and benchmarks remain outside its scan.

Core packages

Surface Status Coverage Runtime target Notes and accepted next gaps
Core IO package Partial Console helpers, prelude/explicit namespace dependencies, old callable rejection, removed public IO, input metadata/type-checking, HTML-JS input helper emission and backend unsupported-call diagnostics. Frontend / JS / HTML-Wasm validation @core/io exposes io.print, io.line, io.debug, io.warn, io.error and io.input.*. The prelude injects io as a compile-time namespace alias, not a runtime value. Its future scope and the surface that should remain permanently preluded require a dedicated design pass before major expansion. Filesystem, network, timers, event queues and targeted input sources remain candidate inputs to that review rather than pre-assigned additions or separate packages. Queued io.set_title is a later browser-capability document-title call, not current IO support; see the deferred row below.
Core collections package Partial Broad literal, fixed/growable mutation, indexing, fallibility, AST/HIR call target, JS helper and diagnostic coverage. Frontend / JS / HTML-Wasm validation @core/collections provides the compiler-owned collection operation identities behind fixed and growable collection members. Common non-sorting gaps still need a focused package audit. The accepted stable-by-default sorting contract is owned by its specialised package plan and remains blocked on final mixed-backend collection support.
Core math package Partial Targeted direct, aliased, namespace, const, arity, type, missing-symbol, unbound access, finite-result boundary and HTML-Wasm unsupported-path coverage. JS / HTML-Wasm validation @core/math exposes Float math functions and scalar constants. It requires an explicit dependency clause. HTML-JS routes every single-Float external result through the shared finite-result boundary, rejecting NaN and both infinities before ordinary Moth code observes them. Common mathematical gaps should be filled before expanding into specialised APIs.
Core text package Partial Targeted runtime, JS helper, arity, type-error, edge-case, unsupported-builder and Wasm-unsupported coverage. JS / HTML @core/text currently exposes length, emptiness, containment, prefix and suffix checks. text.length counts Unicode scalar values with the same unit as Char. The accepted next v1 slice adds scalar-indexed character access and slicing, first/last search positions, match counting, Unicode-whitespace trimming and literal replacement after native result slots and Core const evaluation land. Collection-valued split/join/lines/character surfaces wait for stable collection-valued binding signatures. Fallible char_at and slice can gain Rust parity immediately but compile-time evaluation waits for an accepted fallible Core evaluator. Unicode casing, case folding, normalization and grapheme operations wait for a pinned Moth-owned Unicode data policy rather than inheriting host Unicode versions. Regex and locale-sensitive text remain separate future design areas.
Core random package Partial Targeted dependency, JS helper, runtime smoke, arity, type-error and Wasm-unsupported coverage. JS / HTML @core/random exposes random Float and inclusive random Int helpers. Seeded random and additional common distributions remain deferred. Exact generator algorithm identity is not currently a cross-backend semantic promise, so JS may use a backend-local implementation while portable observable contracts remain stable.
Core time package Partial Targeted dependency, direct alias, namespace, helper, runtime smoke, fallible parse/catch, arity/type diagnostic, old-name rejection, opaque-field rejection and backend validation coverage. JS / HTML @core/time exposes opaque Duration, TimeMark and Timestamp values plus the first JS-backed time helper slice. Calendar, civil-time and time-zone APIs remain future work. Time values, parsing and other deterministic semantics must stay backend-neutral rather than inheriting JavaScript-specific behaviour.

HTML project builder

Surface Status Coverage Runtime target Notes and accepted next gaps
HTML project builds Supported Broad routing, API-only artifact filtering, document shell, metadata, config, output cleanup, external JS glue, page-fragment and resource-output coverage. HTML / JS This is the release-critical project builder. Only roots with HTML artefact activity participate in page, runtime asset, resource-output and homepage planning. Backend implementation and HTML-Wasm progress remain on the compiler progress matrix.
Moth template .mtf content assets Partial Targeted compiler-integrated dependency binding, synthetic content constant, markdown folding, module-root re-export, direct API, diagnostics and integration coverage. HTML builder / frontend .mtf files are builder-supported source assets that synthesize one private compile-time content #String constant from an implicit $md template body. Nested templates without an explicit directive also default to Markdown and explicit directives override that default. They bind extensionlessly into .moth and must fully fold.
Plain Markdown .md content assets Supported Broad extensionless dependency, direct alias, module-root re-export, parser options, raw HTML, literal links/images, collision, direct-extension and module-root rejection coverage. HTML builder / frontend .md files render to HTML at compile time and synthesize one private content #String constant. They do not parse Moth declarations, interpolation, templates, frontmatter or metadata.
Builder-supported source file kinds Partial Targeted moth template and Markdown source-kind registry, extensionless resolution, unsupported-kind diagnostics, source discovery and tokenizer/preparation coverage. Stage 0 / frontend Builders can declare non-.moth source file kinds that participate in source dependency discovery and frontend preparation. The HTML builder currently implements .mtf and plain Markdown .md content assets.
HTML Builder package @html Partial Source-backed Builder package registration plus docs-site use across templates, style helpers, tables, code blocks and canvas wrappers. HTML builder @html provides compile-time HTML helpers and source-owned wrappers over lower-level builder bindings such as @web/canvas. It should grow only where helpers are broadly useful to HTML projects rather than becoming a general web framework.
Canvas package @web/canvas Partial Binding-backed package registration, opaque handle types, runtime assets/glue and current drawing API coverage. HTML / JS The current surface covers canvas element management, 2D context state, rectangles, paths, text, gradients, patterns, image drawing, image data and pixel access. Canvas is deliberately allowed a broader expansion target than most packages because visuals and animation make it a useful Moth language and runtime stress-test surface.

Accepted deferred package and builder work

Surface Status Coverage / diagnostic direction Notes
Core Text collection-valued operations Deferred Keep final collection signatures unavailable rather than exposing opaque JS handles. split, join, lines and an eventual character iteration surface wait for stable collection-valued binding signatures or another final source-backed route.
Core Text Unicode transforms Deferred Exact search and current transforms remain host-version-independent. Unicode lowercase/uppercase, case folding and NFC/NFD/NFKC/NFKD normalization wait for one pinned Moth-owned Unicode data policy and generated first-party tables shared across implementations. Host JavaScript or Rust Unicode versions do not define Core semantics.
Core Text grapheme operations Deferred Existing length and positions remain Unicode-scalar based. Grapheme-aware length, iteration and slicing wait for an accepted explicit API plus pinned Unicode segmentation data. They do not replace the scalar semantics of length, char_at, search positions or slice.
Core Text fallible constant evaluation Deferred Runtime APIs keep normal Error semantics; no temporary optional forms are introduced. Rust parity functions for fallible text helpers can exist with the package, but compile-time evaluation of char_at and slice waits for an accepted compiler-owned fallible Core evaluator.
Source-backed package HIR caching Deferred No precompiled source-backed package cache. Source-backed packages are compiled from source each build. Caching stays deferred until package identities and the package system are stable.
Package manager Deferred No package manager, remote registries, lockfiles or dependency resolver. Project dependency declarations, resolver/catalog handoff and package-manager foundations are owned by their later roadmap work. This matrix records status only and does not design that system.
Binding-backed JS package expansion Deferred JS provider diagnostics reject unsupported public binding forms. The HTML builder supports annotated single-file .js imports and builder-owned JS-backed packages. Additional binding forms should be added only when their package contract is clear and they fit existing package ownership.
Generic binding-backed package functions Deferred External signature validation rejects unsupported generic binding-backed surfaces. Binding-backed packages currently expose concrete functions, opaque types and constants only. Generic binding-backed functions remain deferred and must not be introduced just to flesh out a package.
$html_builder configuration Deferred None Closed config-only HTML settings directive with required singleton invocation for authored HTML directory projects. Bare $html_builder uses defaults. Current grouped html records remain implemented. Compiler-wide $project / $config status lives in @../ (Progress).
Root-only $page and explicit purpose Deferred None Accepted queued HTML entry declaration. One normal-root $page per directory, metadata cutover from reserved page_* names, and command-specific no-page rules. Current HTML entries still come from implemented root activity and reserved page metadata.
Browser-capability io.set_title Deferred None Queued Core IO call: one String-content input, no value result, HTML-JS host capability, pre-lowering rejection on unsupported reachable targets. Not a silent no-op. Current IO helpers are unchanged.

Maintenance rule

Keep this page concise but useful as a handoff between package iterations.

  • Record the important common missing operations while a package is being worked on.
  • Move implementation sequencing and unaccepted package ideas to docs/roadmap/roadmap.md.
  • Keep backend implementation status on the compiler progress matrix.
  • Keep package API explanations and examples in docs/src/docs/packages/**.
  • Add a new package row only after that package's scope and semantic contract have been deliberately considered.
  • Do not invent package origins or tiers to classify importance. Use only the package model accepted by the canonical package documentation.
