PROGRESS MATRIX

This page tracks current implementation and target status for Moth's accepted core language, compiler, build-system and backend design. Package APIs and project-builder-specific behaviour are tracked separately in Packages and Builders Progress.

Accepted deferred surfaces may appear here. Open design questions and outside-scope mechanisms do not. Permanent language exclusions live in Design scope.

Invalid-form diagnostic coverage may appear inside the row for the intended feature. This page is not a full language reference, roadmap, exclusion inventory or test manifest.

The compiler and memory design references may describe accepted end-state architecture that has not fully landed. This matrix determines what the compiler supports today.

JS/HTML delivers most of the accepted implicit-failure and entry Error! contract: private propagation, expression-wide catches, success-only runtime fragment publication and moth dev entry-error reporting. Wasm rejects recoverable numeric failure explicitly. Conservative proof discharges Add, Subtract, Multiply and Negate over fixed-width integer domains with full-range containment; other domains are excluded from that discharge; the checked-arithmetic reference states which operations can fail.

Use this together with tests/cases/manifest.toml when changing language features.

How to read and edit this page

  • Keep rows focused on current compiler, core build-system and backend behavior.
  • Put package and project-builder status in Packages and Builders Progress.
  • Put user-facing explanations and examples in docs pages under docs/src/docs/**.
  • Put implementation sequencing, active project plans and proposals that have not been accepted as design in docs/roadmap/roadmap.md.
  • Put accepted end-state architecture in the relevant compiler, memory or language design reference even when the implementation is incomplete.
  • Put compiler architecture and stage ownership in docs/compiler-design-overview.md.
  • Put contributor workflow, benchmarking and tooling details in CONTRIBUTING.md.
  • Prefer short coverage summaries over long fixture lists unless fixture names identify a fragile surface.
  • Use the status labels from this page's legend. Put nuance such as removed, reserved, not Alpha or backend-specific in the notes column instead of inventing new status labels.

Alpha target

The supported Alpha target is:

  • frontend parsing and diagnostics
  • typed AST construction
  • HIR lowering
  • borrow validation
  • JavaScript backend
  • HTML project builder
  • docs-style static site generation

Assertions Partial Broad parser, diagnostics, HIR lowering, backend artifact and integration coverage. JavaScript and HTML evaluate reachable runtime messages lazily on the failure edge; HTML-Wasm accepts default, fully folded and unreachable literal-true runtime messages but rejects reachable runtime construction. Literal-true messages are fully type/generic/evidence checked and normalized, then replaced with typed none before HIR, so no TIR, runtime handoff, reactive metadata, generated request or executable fact is published. Message construction cannot escape its evaluation through !, ?, return, break or continue. Authored propagation locations remain distinct from ordinary call mapping. assert(false) is statically terminal.

External and compiler-owned builtin calls remain positional-only. Source-authored return-alias syntax has been removed. Ordinary return preserves allocation identity, explicit copy creates independence and each call result receives a separate caller binding. Current multi-return alias analysis may conservatively over-approximate relationships between returned values, which can produce stricter alias diagnostics.

Collections Supported Broad literal, mutation, builtin method, indexing, loop, result, fixed-capacity, fixed overflow and catch, growable handling rejection, AST/HIR, JS helper and diagnostics coverage. JS / HTML Growable {T} and fixed {N T} collections are distinct semantic types. Fixed capacities accept positive literals or bare visible #Int constants. Growable push is infallible, returns no value and rejects catch and postfix !; allocation exhaustion traps or aborts rather than entering Error!. Fixed push is fallible only when the collection is full and reuses the existing capacity error. get, set and remove stay fallible, and length stays infallible. One source spelling resolves push from the receiver's collection shape in the AST, HIR lowers distinct call targets and the JS runtime exposes separate growable and fixed helpers. HTML-Wasm collection lowering remains deferred and target-rejected.

HTML-JS canonicalizes every String-like key to canonical content, including template-backed keys, and supports canonical same-typed lookup and duplicate rejection for these source keys. Constants and compile-time folding Supported Broad top-level constant, dependency sorting, template folding, numeric folding, const-record, anonymous const-record, external constant, config and diagnostics coverage. Focused Int32/Int64 consumption tests cover copied constants, imported nominal and anonymous const-record leaves and configuration-origin diagnostics. Const records are compile-time field-access-only values. Type aliases Partial Broad builtin, imported, collection, option, generic instance, alias-to-alias, remap, fixed-capacity constant, trait-requirement and diagnostic coverage. Arithmetic, explicit casts and copy Partial Broad arithmetic, precedence, checked numeric, cast parser/AST/HIR/JS, const-folding, explicit copy and diagnostics coverage. Fixed-width promotion/compatibility and numeric constant folding are covered. Frontend / HIR / JS / HTML / HTML-Wasm Runtime Int/Float numeric operations lower through checked HIR operations. Fixed-width and Byte cast policies, fixed-width operator typing and numeric constant folding are implemented in the frontend/HIR. HTML-JS executes fixed-width numeric and Byte runtime values, private inferred failure and builtin Error materialisation, including typed compound write-back conversion failure. HTML-Wasm executes supported fixed integers, Byte, F16, F32/F64 and profile-selected Int/Float scalar values and comparisons, but explicitly rejects recoverable numeric failure rather than substituting traps. Conservative semantic proof discharges Add, Subtract, Multiply and Negate over fixed-width integer operand and result domains with full-range containment (for example U8 + U8 -> U32): proven-safe operations carry no implicit failure contributor, request no recoverable capability and compile on Wasm. Divide, IntegerDivide, Remainder and Power, and bounded results outside the domain, stay checked. Float, Dec, Int and Byte are excluded from this discharge; the @../numbers/#checked-arithmetic (checked-arithmetic reference) states which of those operations can fail. The proof is type-domain based and profile-free, identical in debug and release and across numeric profiles. F16 scalar values use a finite F32 computation carrier and compact two-byte storage with portable conversion/rounding. Supported infallible numeric expression casts include the existing casts not involving F16, integer -> F16 and widening F16 -> F32/F64, plus Byte -> U8 and U8 -> Byte. HTML-Wasm also executes NumericToString expression casts for profile Int and fixed signed/unsigned integers. F32/F64 -> F16 narrowing and numeric-to-numeric casts from F16 other than widening to F32/F64 remain target-gated. Float formatting and boundary-validation guards remain fatal integrity checks, not implicit failures. Other fallible casts, other defined builtin runtime conversions involving Bool, Char, Error or String (including Char -> Int and String-to-numeric parsing), statement-form casts, source-level external Float imports and fixed-scalar aggregates remain target-gated. Dec arithmetic, exact negation and cast policies are implemented in the frontend. HTML-JS executes exact mixed operations and comparisons against profile Int and all eight fixed integer types, rounded half-even per operation. Integer-to-Dec and scale widening are infallible. Scale narrowing and Dec-to-integer conversions are exact and fallible. HTML-JS String-to-Dec conversion parses the whole existing numeric grammar exactly, and HTML-JS formats Dec canonically. HTML-Wasm rejects reachable Dec values and signatures, including nested types and generated-function uses. Unreachable private helpers do not gate the target. Explicit cast uses compiler-owned builtin cast policies and evidence. Const Error materialisation and branching const catch handlers remain deferred. Folded eligible numeric catches retain their semantic eligibility. Conservative integer proofs elide only proven JS integer-operation/narrowing predicates and supported Wasm integer-operation predicates (ProvenSafe). Evaluation order and required carriers remain unchanged. JS canonicalises exact-integer Number zero and keeps BigInt exact. Missing or profile-mismatched facts retain checks. Power, Byte, float and Dec checks remain. Wasm casts and Error-mode arithmetic remain target-gated, with no Wasm narrowing support.
Float formatting and boundary validation Partial Frontend folding and external-boundary tests, paired HTML/HTML-Wasm source fixtures at default and Int32/Float32 profiles (both 2/2), generated-Wasm formatter checks for all finite F16 encodings and selected F32/F64 boundary and random bits, plus non-finite traps. JS / HTML / HTML-Wasm The frontend folds Float text. HTML-JS uses Moth-owned Float formatting for runtime template interpolation and casts, and validates external Float success returns. Formatting and boundary-validation guards are not implicit failures or catch producers: they trap unless a source-declared builtin Error! contract returns them. Synthetic start's compiler-owned Error! slot does not make them recoverable. HTML-Wasm preserves these guards after carrier conversion and formats Float/F16/F32/F64 values at their own precision. Source-level external Float imports and String-to-numeric parsing remain target-rejected.

Strings, coercion and IO/template boundaries Partial Broad quoted-escape, string-content coercion and IO/template rejection coverage, plus targeted external StringContent signature coverage. Frontend / JS Quoted strings decode only \\, \", \n, \r and \t. Invalid escapes are rejected by the tokenizer. Template heads and reusable external string-content signatures accept supported string values. AST rejects source String + String and no longer folds compile-time string addition. Accepted design rejects source string concatenation with +; templates remain the canonical concatenation form.
Borrow validation and local last-use analysis Partial Broad borrow, aliasing, mutable/exclusive access, branch merge, loop, short-circuit, future-use, optional-transfer, advisory drop-site, hashmap, aggregate-storage, reactivity and adversarial coverage. Phase 1 establishes the permanent `boracle` developer feature, shared `problem` and `last_use` seams and an opt-in `just boracle` validation lane. The reference facility now extracts validated HIR into immutable normalized problems, constructs typed `OriginRelations` as the only origin-overlap owner, answers pair-local `query_overlap` decisions with positive disjointness evidence and derives alias/provenance loans that retain structural place overlap separately. It connects parameter-aware origin flow to use-driven liveness, origin/loan last-use and exact after-event final-use candidate queries. Its compiler-owned source service covers calls, aggregates, maps, fallible flow, branch/loop paths and bounded generated copy/rebind metamorphic properties with deterministic reduced failure reports and classified comparisons against the deliberately shared Alpha subset. Composable experiment selection uses `boracle-reference-v1` with a sorted empty-by-default experiment set; the only current named experiment, `dead-exclusive-loan`, remains feature-gated developer research and is not production language support. A second executable semantics, the bounded operational oracle, now executes the same normalized problems with explicit dynamic generations and capability intervals, enumerates branches and bounded loops deterministically, always reports truncated exploration as inconclusive and classifies its result against the static solver so static acceptance plus an enumerated runtime conflict is a required failure. A seeded generator and a class-preserving reducer turn generated disagreements into minimal reproducible cases. The oracle is feature-gated developer reference infrastructure and never user-facing borrow support. The alpha checker remains the normal compiler authority; Boracle never changes default acceptance. Lifetime-region validation, retained-edge analysis, REC integration, memory-plan-driven cleanup and the optimized production checker remain deferred. HIR analysis / all backends Shared and exclusive access enforcement is implemented and mandatory on every backend. Path-sensitive future-use facts drive optional transfer, and unproven or path-dependent transfer correctly falls back to borrowing. Per-block future use is a liveness fact, so an alias that every path redefines before its next read stops blocking mutation, including across a loop back-edge. Accepted incomplete work: loop final-iteration facts, detached stored-result transfer and the complete affine-transfer contract are not implemented, and drop facts remain advisory rather than memory-plan-driven. Complete when path-sensitive transfer and final-use facts are complete.
Result provenance and retention summaries Partial Targeted return-alias and fresh-result summary coverage. HIR analysis / link planning Public summaries currently distinguish fresh result roots, parameter aliases and an imprecise unknown case. Accepted incomplete work: projection results, detached stored results, result-to-result aliases, independent result graphs, retained-parameter and outlives constraints, retention and cardinality effects, whole-domain kill effects, outcome-sensitive effects and frontier-enabling effects are not exported yet. Complete when stable complete summaries cross module and package boundaries with no unknown topology-relevant provenance.
