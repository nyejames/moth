Documentation / Casts

Casts

A cast converts a value for an immediate typed destination. Moth doesn't use constructor-like conversions such as Int(value), and it doesn't infer a target from distant code.

The receiving type names the target. cast, cast! or catch makes the failure path visible beside the conversion.

Choose the explanation level: Cast syntax

Cast syntax

A cast converts a value to the type expected by its destination.

parse_count |text String| -> Int, Error!:
    return cast! text
;

ratio Float = cast 3

Read the first conversion as:

> Convert text to the Int required by the function's return slot.

Use:

  • cast when the conversion cannot fail
  • cast! when conversion failure should leave through a compatible builtin Error! return
  • cast ... catch: when failures in the operand or conversion should be handled here

catch covers the complete cast expression, not only the conversion. It can handle arithmetic and builtin Error! calls inside the operand too. A cast cannot combine cast! and catch, and invalid conversions remain source errors. See Fallible casts for recovery rules. Progress owns current support.

Moth does not use Int(value) or String(value) as conversion syntax.

cast performs an explicit conversion to a compiler-supported builtin target.

The target comes from the immediate typed receiving boundary. Every numeric type spelling is a valid target where its source-target policy allows the pair.

Moth adds no numeric conversion syntax. There is no parenthesised target, no target after the expression and no constructor-like conversion form.

octet U8 = 42
count U64 = cast octet
half F16 = cast octet
raw Byte = cast octet
money Dec2 = cast count
total Uint = 1 + 2
back Int = cast total catch then 0

Each conversion above is infallible except the last: U8 fits U64, Byte and the F16 finite range, and a whole number scales exactly into Dec2. The Uint-to-Int cast is fallible and needs its handler. Fixed-width and Byte cast policies and evidence are implemented in the frontend; the frontend also implements compiler-owned Uint and Dec cast policies. HTML-JS executes fixed-width, Byte, Uint and Dec runtime casts. Its exercised Dec casts include infallible integer-to-Dec and scale widening; scale narrowing and Dec-to-integer conversions are exact and fallible. String-to-Dec parsing is fallible and consumes the whole existing numeric grammar exactly; Dec-to-String uses canonical formatting. Uint casts use complete semantic ranges: Uint -> Int and Int -> Uint are fallible in both directions, Uint -> Float is direct and infallible, and same-type Uint casts stay invalid.

HTML-Wasm executes infallible numeric expression casts that do not involve F16, as well as integer-to-F16 and widening F16-to-F32/F64, plus Byte -> U8 and U8 -> Byte. F32/F64-to-F16 narrowing and other numeric-to-numeric casts from F16 remain target-gated. It supports infallible integer-to-String expression casts from profile Int and fixed signed/unsigned integers. Float/F16/F32/F64-to-String formatting is a separate integrity guard, not implicit numeric failure: it halts on a non-finite input unless a declared builtin Error! contract returns it.

HTML-Wasm rejects reachable Dec values and signatures, including nested types and generated-function uses; unreachable private helpers do not gate the target. On HTML-Wasm, remaining fallible casts, String parsing, conversions involving Bool, Char or Error (including Char -> Int), statement-form casts, source-level external Float imports and their finite-boundary validation, and reachable ReturnError FormatFloat/ValidateFloat remain target-rejected. See Progress for current support.

parse_count |text String| -> Int, Error!:
    return cast! text
;

ratio Float = cast 3
label String = cast ratio

Forms

value Target = cast expression
value Target = cast! expression

value Target = cast expression catch:
    then fallback
;

value Target = cast expression catch |err|:
    then fallback
;
  • Plain cast without an enclosing handler requires infallible evidence.
  • cast! requires fallible evidence and explicitly propagates through a compatible builtin Error! slot, including start at the top level.
  • cast ... catch: recovers the complete selected expression, including operand evaluation and the conversion. A fallible conversion needs fallible evidence; an infallible conversion can still have a failing operand.
  • Cast syntax does not contain the target in parentheses or after the expression.

Implicit failure and builtin Error! can share the cast expression's handler. cast! and catch on the same cast remain invalid. Catch does not legalise invalid cast evidence. See Fallible casts.

Removed conversion constructors

These scalar conversion forms are invalid:

Int(value)
Float(value)
Bool(value)
String(value)
Char(value)

Every numeric type name follows the same rule. U8(value), U64(value), F16(value), Byte(value) and Dec2(value) are a type name applied to an argument, never a conversion.

Error(...) remains a real builtin constructor:

err = Error("Missing number", 200)

Conversion to Error still uses cast when conversion rather than construction is intended:

err Error = cast "Missing number"
Choose the explanation level: Cast targets

Cast targets

A cast needs a clear destination type.

These are supported cast targets:

  • Bool
  • the numeric types: Int, Uint, Float, the fixed-width integers and binary floats, Byte, and the exact Dec family
  • String
  • Char
  • Error

Uint converts implicitly to Float at value-receiving and mixed-operator boundaries, and explicitly with cast in both directions with Int, Float, fixed integers and the Dec family. Uint and Int need an explicit cast between each other even when the values would fit.

Not every source type can convert to every target. Byte and U8 convert in both directions without failing, and other Byte numeric conversions go through U8. HTML-JS executes casts to these targets. Wasm still gates fallible casts and other remaining conversions. See Progress for current support.

An annotation gives the cast its target:

count Int = cast! text
label String = cast count

Without that annotation, the compiler cannot know which conversion you want:

count = cast text

The second form is invalid.

Casts can also receive a target from a function parameter, return slot, field or another immediate typed destination.

Explicit casts target compiler-supported builtin types:

Bool
Int
String
Char
Float
Error

Numeric targets are the profile-selected Int, Uint and Float, the fixed integer and binary float types, Byte and the Dec family.

integers:      Int, Uint, I8, I16, I32, I64, U8, U16, U32, U64
binary floats: Float, F16, F32, F64
other:         Byte, Dec, Dec0, Dec1 through Dec256

A type being a valid target does not mean every source type can convert to it.

Builtin cast table

  • Int -> Float (infallible): Numeric conversion to finite Float
  • Uint -> Float (infallible): Direct unsigned conversion to finite Float at the selected precision, also available implicitly at value-receiving and mixed-operator boundaries
  • Int -> String (infallible): Base-10 signed integer text
  • Uint -> String (infallible): Base-10 unsigned integer text
  • Float -> String (infallible): Moth's stable float formatter
  • Bool -> String (infallible): "true" or "false"
  • Char -> String (infallible): One Unicode scalar as UTF-8 text
  • Char -> Int (infallible): Unicode scalar code point
  • String -> Error (infallible): Error message from the text with U32 code 0
  • Error -> String (infallible): The error message only
  • Float -> Int (fallible): Truncate toward zero, then require the Int range
  • Float -> Uint (fallible): Truncate toward zero, then require the selected unsigned range. -0.5 truncates to zero and succeeds; -1.0 fails
  • Uint -> Int (fallible): Exact conversion, requiring the selected signed range in every profile
  • Int -> Uint (fallible): Exact conversion, requiring the selected unsigned range in every profile
  • Uint -> Dec and Uint -> DecN (infallible): Exact integer conversion using the full unsigned value
  • Dec and DecN -> Uint (fallible): Exact integrality and unsigned range required
  • String -> Uint (fallible): Parse the complete unsigned whole-number grammar, rejecting -0 and any non-whole spelling
  • Int -> Char (fallible): Require a valid Unicode scalar value
  • String -> Int (fallible): Parse the complete Moth integer text grammar
  • String -> Float (fallible): Parse the complete numeric grammar and require a finite result
  • String -> Bool (fallible): Trim surrounding whitespace, then accept exactly lowercase true or false
  • String -> Char (fallible): Require exactly one Unicode scalar

Uint has no direct builtin conversion with Byte, Char or Bool. Int and Uint need an explicit cast between each other in both directions, even when the values would fit.

Same-type casts are invalid, including Uint -> Uint.

No other builtin source-target pair is implied by the target list.

Numeric conversion is then classified by the complete source and target types.

  • Fixed integer to fixed integer is infallible when the complete source range fits the target range and fallible otherwise. U8 -> U16 and U8 -> I16 are infallible. U16 -> U8 and I8 -> U8 are fallible.
  • Uint converts to and from fixed integers with an explicit cast, infallible exactly when the complete source range fits the target range.
  • Int, Uint, Float and fixed-width values require an explicit cast between distinct types, even at a matching representation. Infallibility follows the complete ranges, so Int -> I32 is infallible only when the selected Int width fits I32, and Uint -> U32 is infallible only under a 32-bit Int profile.
  • Integer to F32 or F64 is infallible and may round. This covers both Int and Uint sources, and Uint64 converts directly without a binary64 intermediate that could double-round. Integer to F16 is infallible only when the complete source range fits the F16 finite range, so I32 -> F16 is a fallible finite-range conversion.
  • A conversion to a binary float of greater precision is infallible. A conversion to a narrower precision is fallible and rounds once, directly from the source precision. F64 -> F32, F32 -> F16 and F64 -> F16 are all fallible, and F64 -> F16 is never a two-step F64 -> F32 -> F16 conversion. Float uses the precision selected by the numeric profile.
  • Float to integer is fallible. It truncates toward zero, then checks the target range. F64 -> I64 is one example, and Float -> Uint additionally rejects negative results below zero while -0.5 still truncates to zero and succeeds.
  • Byte -> U8 and U8 -> Byte are infallible in both directions. Other numeric Byte conversions compose through U8 rather than forming a separate conversion lattice.
  • Integer to Dec or any DecN is exact and infallible, including Uint with its full unsigned value. Scale widening is exact and infallible.
  • Scale narrowing and Dec or DecN to integer are fallible exact conversions, including to Uint. Removed fractional digits must be zero and the integer must fit its explicit or profile-selected target.
  • Every numeric target accepts String through the complete numeric text grammar (fallible), including Uint with unsigned whole-number spelling. Dec and DecN parsing is exact at the target scale.
  • Every numeric target converts to String (infallible) through its canonical text, including unsigned Uint formatting with zero as 0. Byte text conversion composes through U8, covering parsing and formatting.

Numeric conversion exactness

A cast does not promise universal exactness. Binary float conversions round to nearest, ties-to-even. Uint64 converts directly at the destination precision without a binary64 intermediate that could double-round. Float to integer truncates toward zero before the integer range check, so this conversion does not use the float-narrowing failure rule. Precision loss alone never fails a binary-float precision narrowing, and only a rounded non-finite result fails one.

Integer-to-integer conversion preserves the value exactly, including both Int and Uint sources. Dec scale widening is exact; scale narrowing and Dec-to-integer conversion are exact or fail, never rounded. Same-type casts remain invalid.

No modulo, wrapping or saturating conversion is added to the language.

Implementation status

This reference owns the accepted cast contract. Progress owns current compiler and backend support. The Alpha compiler resolves the Bool, Int, Uint, Float, String, Char and Error targets, plus the fixed-width integer, fixed binary float and Byte targets for numeric and text conversions. Fixed-width casts fold at compile time. The frontend implements compiler-owned Uint and Dec cast policies; HTML-JS executes fixed-width, Byte, Uint and Dec runtime casts. The exercised HTML-JS Dec casts include infallible integer-to-Dec and scale widening; scale narrowing and Dec-to-integer conversions are exact and fallible. String-to-Dec parsing is fallible and consumes the whole existing numeric grammar exactly; Dec-to-String uses canonical formatting. The exercised HTML-JS Uint casts include Uint/Int and Uint/fixed-integer conversions in both directions, direct Uint-to-Float conversion, Uint/Dec conversions and String/Uint text conversion with unsigned formatting.

HTML-Wasm executes infallible numeric expression casts that do not involve F16, as well as integer-to-F16 and widening F16-to-F32/F64, plus Byte -> U8 and U8 -> Byte. F32/F64-to-F16 narrowing and other numeric-to-numeric casts from F16 remain target-gated. It supports infallible integer-to-String expression casts from profile Int and fixed signed/unsigned integers. Target source

The target must come from the immediate typed boundary.

Valid target boundaries include:

  • an annotated declaration or assignment
  • an explicit return slot
  • a concrete function parameter
  • a struct or choice field
  • a default value
  • a typed collection or map entry
  • a compiler-owned typed assertion argument slot (condition: Bool or message: String?)
  • a then arm whose enclosing value-producing block has an explicit receiver

Unsolved generic parameter slots are not cast targets. A generic struct or choice field becomes one only after the expected result fixes its parameter, as in boxed Box of U16 = Box(cast small). Generic inference does not look through cast.

These positions do not supply cast targets:

  • conditions
  • loop conditions
  • template interpolation
  • operator operands
  • expression statements
  • untyped declarations
-- INVALID: these positions do not supply cast targets
value = cast source

if cast value:
    io.line("invalid")
;

[: [cast value]]

The forms above are invalid because no immediate builtin target exists.

Optional receiving contexts

A T? receiving context casts to inner T, then applies normal contextual wrapping to T?.

Optional source values are not automatically unwrapped.

In:

target T? = cast source catch:
    then fallback
;

the recovery handler produces inner T. then none is invalid because recovery happens before optional wrapping.

Numeric and text details

  • String -> Int, String -> Uint, String -> Float and every other numeric text conversion consume the whole string.
  • Numeric text rejects surrounding whitespace, uppercase exponent markers, unary plus, malformed separators, malformed exponents, NaN and infinity spellings. Unsigned Uint text additionally rejects a leading -, including -0.
  • Binary float text conversion additionally rejects a grammar-valid non-finite result.
  • Every integer target materialises inside its own range. The Int and Uint ranges follow the selected profile, with Uint spanning the unsigned width.
  • Uint formats as unsigned base-10 text, with zero always formatted as 0.
  • Binary float to String normalises negative zero to 0 and uses lowercase exponent formatting when exponential notation is required.
  • Dec to String uses canonical Dec text with fractional trailing zeroes trimmed, no exponent notation, no negative zero and a leading zero before a fractional value.
  • Byte and U8 remain nominally distinct. No receiving boundary widens one into the other silently.
  • Contextual Int -> Float promotion remains separate from explicit casting, though explicit cast is valid from a naturally Int source to a Float target. Contextual Uint -> Float promotion is likewise separate from its explicit cast form.
Choose the explanation level: Fallible casts

Fallible casts

Some conversions can fail. Text might not contain a number and a Float might not fit inside Int.

Use cast! with a compatible builtin Error! return path:

parse_count |text String| -> Int, Error!:
    return cast! text
;

Use catch when this part of the program has a sensible fallback:

count Int = cast text catch:
    then 0
;

Choose one path. A cast cannot use ! and catch at the same time.

The handler covers both the conversion and evaluation of its operand. Arithmetic and builtin Error! calls inside that operand can share the handler:

narrow |left U32, right U32| -> U8:
    value U8 = cast left + right catch then 0
    return value
;

This recovers addition overflow as well as a result that does not fit U8. Parentheses are not required. A bound error name has type Error; typed errors keep their original message and code. Custom errors cannot mix with these built-in failures.

A catch does not make an unsupported conversion valid. Numeric work known to be invalid still produces a compile-time diagnostic. See Progress for current support.

Converting to a narrower binary float is not automatically a failure. It fails only when the rounded result is not finite, so losing precision is not an error by itself. Converting a float to an integer is different: it truncates toward zero and then checks the integer's range, so a value outside that range fails.

A fallible cast can propagate through builtin Error! or recover locally.

Propagation

parse_count |text String| -> Int, Error!:
    return cast! text
;

cast! requires fallible cast evidence and a compatible builtin Error! return path. It remains explicit propagation, including at the top level where start supplies that slot. A custom E! slot does not automatically convert the failure.

Local recovery

count Int = cast text catch:
    then 0
;

other_count Int = cast text catch |err|:
    io.line(err.message)
    then 0
;

A recovery handler must produce the success value required by the receiving site or leave explicitly with return or return!.

Expression-wide recovery

cast expression catch protects the complete operand evaluation and the conversion. Arithmetic, receivers, arguments and nested calls inside the operand belong to the same selected expression. Parentheses are not required:

narrow |left U32, right U32| -> U8:
    value U8 = cast left + right catch then 0
    return value
;

This handler recovers both U32 addition overflow and failure to narrow the result to U8. The addition still computes in its own U32 result domain.

Implicit failure and builtin Error! from the operand or conversion may share the handler. A bound error name has type Error. A typed Error retains its message, code and identity, including code 0. Compatible typed calls under the handler do not need per-call postfix !. Custom typed errors cannot share this handler with implicit failure or a conversion's builtin Error!. See Catch and recovery for compatibility and placement rules.

A catch on a compound assignment's right-hand expression does not protect the later compound arithmetic or conversion back to the target type. Those remain separate implicit-failure checks, and the store happens only after success. See Checked arithmetic.

Rules

  • cast! expression catch: is invalid.
  • Propagation and local recovery are mutually exclusive.
  • The handler protects operand evaluation as well as the conversion.
  • An infallible conversion can use expression catch when its operand can fail.
  • Optional receiving contexts recover inner T, then wrap the successful or recovered value into T?.
  • then none is invalid in a cast recovery handler targeting T?.
  • Evidence is static. A compiler proof that a value is safe can fold a cast or remove its runtime check, but it never makes an unhandled plain cast legal for a fallible type pair.
  • A catch does not legalise unsupported source-target pairs or invalid cast evidence.
  • Statically known invalid numeric work remains a source diagnostic, even with catch or builtin Error!.

A plain cast without an enclosing handler requires infallible evidence for the selected pair. An eligible expression catch supplies local handling for fallible evidence, not evidence for an otherwise invalid conversion. See Cast evidence and Checked arithmetic.

Choose the explanation level: Cast evidence

Cast evidence

The compiler already knows the built-in conversions.

A user-defined struct or choice can opt into a supported target by providing the required method and declaring explicit conformance.

Label = |
    text String,
|

to_string |this Label| -> String:
    return this.text
;

Label must CASTABLE_TO_STRING

Now a Label can be cast to String at a typed destination.

This stays explicit. Matching method names alone do not create cast support.

Numeric evidence

Builtin numeric conversions are decided by the static source and target types, not by values the compiler happens to know. An integer conversion is exact when the whole source range fits the destination, and fallible otherwise. Byte and U8 convert in both directions without failing. Uint and Int need an explicit cast between each other in both directions, even when the values would fit.

Binary conversions may lose precision by design. Integer-to-float and binary-float precision narrowing round to nearest, ties to even, and float-to-integer conversion truncates toward zero and then checks the target range. Narrowing a binary float fails only when the rounded result is not finite, so precision loss alone is not a failure.

The frontend implements fixed-width, Byte and Dec evidence. HTML-JS executes Dec casts: integer-to-Dec conversion and scale widening are exact and infallible, scale narrowing and Dec-to-integer conversion are exact or fail, and String-to-Dec parsing is fallible. Dec formats to String exactly, including through matching generic cast bounds. HTML-Wasm executes supported infallible numeric expression casts and rejects reachable Dec values. See Progress for target support.

Compiler-owned static traits prove cast availability. The compiler also registers builtin evidence for the builtin cast table.

Trait table

Each source-authored evidence family has one infallible trait and one fallible trait.

  • Int: CASTABLE_TO_INT requires to_int |This| -> Int; TRY_CASTABLE_TO_INT requires try_to_int |This| -> Int, Error!
  • Float: CASTABLE_TO_FLOAT requires to_float |This| -> Float; TRY_CASTABLE_TO_FLOAT requires try_to_float |This| -> Float, Error!
  • Bool: CASTABLE_TO_BOOL requires to_bool |This| -> Bool; TRY_CASTABLE_TO_BOOL requires try_to_bool |This| -> Bool, Error!
  • String: CASTABLE_TO_STRING requires to_string |This| -> String; TRY_CASTABLE_TO_STRING requires try_to_string |This| -> String, Error!
  • Char: CASTABLE_TO_CHAR requires to_char |This| -> Char; TRY_CASTABLE_TO_CHAR requires try_to_char |This| -> Char, Error!
  • Error: CASTABLE_TO_ERROR requires to_error |This| -> Error; TRY_CASTABLE_TO_ERROR requires try_to_error |This| -> Error, Error!

The table shows trait requirement signatures. A source-authored implementation uses an ordinary lowercase this receiver of the concrete type.

Builtin evidence

The compiler registers evidence for the supported builtin source-target table, including Uint, the fixed-width integers, binary floats, Byte and the Dec family.

  • Evidence comes from the complete source and target types. A folded value, a proven range or an optimiser fact never changes the evidence class.
  • A proven-safe fallible cast can fold or lose its runtime check. It cannot make plain cast legal for that type pair.
  • The evidence class is fixed before HIR and backend lowering.

Source-authored evidence

A same-file nominal struct, choice or aligned generic nominal constructor may add evidence for a supported builtin target.

It must provide the required receiver method and declare explicit conformance.

Label = |
    text String,
|

to_string |this Label| -> String:
    return this.text
;

Label must CASTABLE_TO_STRING

label = Label("hello")
text String = cast label

Contract

  • Core cast traits resolve without dependency clauses.
  • They cannot be redeclared.
  • They cannot be imported, exported, aliased or shadowed.
  • They are static contracts, not ordinary value types.
  • Matching method shape alone is not evidence. Explicit conformance is required.
  • Same-file nominal source types may provide explicit evidence.
  • Aligned generic nominal constructors may provide evidence for their concrete instances.
  • Source-authored evidence remains the six families above. The fixed-width numeric types, Uint, Byte and the Dec family carry compiler-owned builtin evidence, and Moth defines no source-authorable cast trait family for them.
  • Infallible and fallible trait pairs for the same target are incompatible through compiler-owned must not metadata.
  • Evidence is resolved before HIR and backend lowering.

Outside cast design scope

  • user-defined cast target types
  • generic cast target parameters
  • external opaque cast targets
  • generic cast traits
  • broad return-type-directed conversion
  • implicit conversion chosen from distant context

Cast traits prove source evidence only. They do not create a general user conversion framework.
