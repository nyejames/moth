Directives

$ introduces a registered compiler or builder directive. Template formatters already use this marker. The accepted general family extends it to configuration, page metadata and later compiler-owned blocks.

Template directives are implemented. The general non-template family is accepted design and is not yet available in the Alpha compiler.

Directives

Accepted queued design. $ introduces a registered compiler or builder directive. Template directives such as $md and $code are implemented. General non-template directives are accepted design and are not yet available in the Alpha compiler. See Progress for current support.

A $ marker is not automatically harmless metadata. Compiler-owned directives may impose real contracts. Builder extensions cannot rewrite functions or weaken language safety.

Current versus accepted syntax

Today, config.moth still uses grouped project and html records, and pages still use reserved names such as page_title. The accepted configuration shape is:

$config
version #String = "0.1.0"

$project(
    name = "my_site",
    version = version,
    entry_root = "src",
)

$html_builder

$page will be legal only on a normal module root, or on an explicitly selected synthetic single-file root. Helper files cannot declare pages.

$page(title = "Moth")

Arguments

  • Supply arguments with $name(arguments).
  • Supply none with $name.
  • Authored empty () is invalid for directives.
  • Ordinary function calls still use f().

$html_builder and $page may be written with no parentheses when every parameter has a default. $html_builder() and $page() are invalid.

Exact signatures live in Project config and Entry metadata and page directives.

Accepted queued design. $ is the general directive marker. Template directives are implemented. General non-template directives, shared directive-call integration, $config, $project, $html_builder and $page are accepted design queued for implementation and are not yet available in the Alpha compiler. Current projects still use grouped project/html records, #Config of T contracts and reserved page_* metadata. See Progress for current support.

$ does not mean harmless metadata. Compiler-owned semantic directives may impose real language or structural contracts. Builder extensions remain constrained: they may supply template directives and consume metadata, configuration and root-purpose facts, but they cannot rewrite functions, change nominal identity, mutate HIR, alter visibility or weaken borrow and lifetime rules.

This page owns general grammar, ownership, context, arguments, attachment and diagnostic distinctions. Exact $project, $config, $html_builder and $page signatures live in the project-structure references linked below.

Marker and non-goals

In the accepted directive design, $ introduces a registered compiler or builder directive, not a binding mode, ordinary expression or source-defined callable. The queued Wiring replacement uses no $ marker. Current reactive bindings remain an explicitly superseded Alpha surface until their removal. There is no accepted with attribute keyword.

Users and source packages cannot define, alias, import or override semantic directives. Frontend names are authoritative. Duplicate registrations and name conflicts are rejected rather than resolved by last registration.

Directive names do not reserve the corresponding ordinary identifiers. $project, $config and $html_builder do not reserve project, config, Config or html_builder outside directive syntax. File semantics for config.moth and the @project dependency root remain separately reserved.

This is not a generic attribute or macro framework. It does not guarantee that every future directive can target every statement.

Ownership and context

$html_builder is HTML-builder-owned and config-only. $project is compiler-owned at the language boundary and config-only. The existing build owner still applies validated project settings. $config is compiler-owned and legal in both bootstrap and specified source declarations.

Arguments

One ordinary call parser, one parameter-slot router and one default validator own directive arguments.

  • A directive with supplied arguments uses $name(arguments).
  • A directive with no supplied arguments uses $name.
  • Authored empty () is invalid for directives, even when every parameter has a default.
  • Ordinary function calls keep f(). Only the directive entry boundary rejects empty parentheses.
  • Arguments and defaults are compile-time values. Runtime values, exclusive or mutable arguments and escaping control flow are invalid.
  • Positional arguments, named arguments, ordering, duplicates, unknown names, commas and multiline whitespace use the shared call owner.
$project("my_site", "0.1.0")
$html_builder

The same project invocation may use named arguments: $project(name = "my_site", version = "0.1.0"). These are alternative spellings of the one required invocation, not two invocations in one config file.

$project() and $html_builder() are invalid. Bare $html_builder still runs required-parameter and default validation.

Template directives move onto the same argument-list owner without changing their existing value domains, head compatibility, formatter behaviour or literal-body modes. Slot labels, indices and helper templates remain compiler-known template argument categories. See Template directives.

Attachment

The descriptor fixes the directive's form.

  • $project and $html_builder are standalone items. They never modify the next declaration.
  • $config modifies exactly one following declaration, ignoring ordinary lexer trivia such as whitespace and -- comments. It does not cross an intervening source item or block boundary.
  • A dangling $config is an error. Duplicate $config modifiers on one declaration are errors.
  • Source modifiers may occupy their own line or precede their target on the same line where ordinary token boundaries permit it. Documentation uses the separate-line form.
  • Standalone directives follow ordinary item boundaries. There is no semicolon statement terminator, comma-separated with clause or new block delimiter.

Unknown, unavailable and placement

Recognition, permitted placement, diagnostics and tooling share one registration authority. Context is checked after name recognition.

  • An unknown directive in active source is an error.
  • A known but unimplemented directive is a deferred-feature diagnostic, never a successful no-op and never a working root purpose.
  • A known directive in the wrong place receives a placement diagnostic.
  • Ordinary static if false does not suppress frontend directive errors. Both branches remain frontend-valid.

Configuration example

Accepted config.moth shape:

$config
version #String = "0.1.0"

$project(
    name = "my_site",
    version = version,
    entry_root = "src",
)

$html_builder

A fixed literal version also works. A contract named version does not satisfy an omitted $project argument. A project field named version does not satisfy a source input contract.

Exact field tables, required version, explicit-only input providers and HTML settings live in Project config and Build configuration values.

Page example

$page is the accepted queued HTML-builder directive for normal-root metadata and page purpose. Ordinary files, support roots, facades and config.moth cannot declare pages. Its implementation will supply the first root purpose in this directive family.

$page(
    title = "Moth",
    description = "A language for creating reliable software",
    lang = "en",
    favicon = @assets/favicon.svg,
)

Bare $page is the default invocation. $page() is invalid. Exact arguments, command policy and runtime title live in Entry metadata and page directives.

Until that implementation lands, operational pages keep reserved page_title, page_head and related declarations.

Future blocks

Future compiler-owned blocks use $name(...): ... ; or $name: ... ;. $async: and $checked: are the accepted future source-block spellings. Recognition of a name for diagnostics is not semantic implementation. Block bodies, $feature predicate algebra, $layout representation contracts, $export migration and $test as a later non-page purpose remain future work.

$feature is structural source selection before graph and declaration publication. Ordinary $config values and static if cannot remove declarations or dependencies. Multi-builder projects wait for $feature.
