MON format

MON means Moth Object Notation. MON syntax names Moth's shared parenthesised argument and value-construction notation. The MON format is the separate serialised-data profile with its own supported values and serialisation rules.

Serialised MON is literal data only. A MON reader never evaluates Moth expressions, including foldable ones. Availability is Rust-only: the bounded decoder and deterministic document/nested-value writers are implemented and public at moth::mon, re-exported from src/lib.rs, over the crate-private src/compiler_frontend/mon/ owner. Another Rust crate can execute the service, but compiled Moth programs have no runtime codec support. Moth-native operations, automatic schema extraction and the static project builder remain deferred separately.

MON format

A small MON document is one root record of literal values. This save record shows the accepted shape: named fields, a nested record, a map, an explicit none and ordinary string data.

format_version = 1,
title = "Strategy",
window = (width = 1280, height = 720),
scores = {"Priya" = 10, "Rob" = 12},
note = none,

The same record may carry explicit outer parentheses. A lone scalar, collection or choice is not a document: put it in a named root field. Encoding fills only exact missing field defaults and emits the completed record in schema order, including explicit none and values equal to defaults. See MON format for the complete literal-data reference.

Strictness is the point. These inputs fail:

-- INVALID: MON never evaluates expressions, including foldable ones
width = 1280 + 0,

-- INVALID: a template is producer syntax, not a MON string literal
title = [: Strategy],

-- INVALID: missing comma between entries
title = "Strategy"
width = 1280,

-- INVALID: `{}` is a collection, never an empty map; use `{=}`
scores = {},

-- INVALID: duplicate keys are rejected, not merged
scores = {"Priya" = 10, "Priya" = 12},

-- INVALID: decimal spelling never converts to an Int target
width = 1280.0,

-- INVALID: unknown record fields fail, even with defaults nearby
titl = "Strategy",

Availability is Rust-only. The implemented Rust caller surface is public as moth::mon, re-exported from src/lib.rs over the crate-private src/compiler_frontend/mon/ owner. Moth-native operations remain deferred separately, and compiled Moth programs have no runtime codec support.

The MON format is Moth Object Notation as serialised literal data: one root record written in the shared MON notation and restricted to literal values. Every value in a completed document must be a supported literal form.

A MON reader never evaluates Moth expressions. Arithmetic, templates, calls, casts, field projections, variables and constant references are rejected even when the compiler could fold them. Rejection happens before expression evaluation, not after evaluating and inspecting a result.

One root record

A complete document contains exactly one record. Its outer parentheses may be omitted. These forms have the same record meaning:

title = "Strategy",
window = (width = 1280, height = 720),
(
    title = "Strategy",
    window = (width = 1280, height = 720),
)

A lone scalar, collection or choice is not a document. Put it in a named root field. The explicit empty root is (). Empty and comments-only input denotes an empty root record. Validation still checks every required field.

Use commas between entries at every level, with one optional trailing comma. Newlines are whitespace, not a separator. Root fields create no bindings, scope or references to earlier fields. After an explicit root, only whitespace and comments may remain. Multiple roots and concatenated documents are invalid. The file and in-memory document grammars are identical.

Records, collections and maps

Values nest recursively subject to resource limits and the receiving schema. Supported values are records, ordered collections, maps, quoted strings, characters, booleans, numeric literal data, none, literal choices and qualified nominal record data.

Record fields have unique identifier labels and explicit = value entries. They are named-only and carry no annotations, declaration qualifiers, mutable markers or shorthand initialisers. () is an empty record, never a tuple or unit value.

MON collections may contain different literal kinds and different record shapes. The receiving schema enforces its element type. Heterogeneous text changes no Moth collection typing rule and adds no Any type to Moth.

Maps preserve insertion order. Keys use the supported Moth map-key families: String, Int, Bool and Char. Bare names are references, not key shorthand, and are invalid as MON map keys. The schema checks the declared key and value types. Map entries and collection items cannot be mixed.

Duplicate keys are rejected rather than keeping the first or last value. Keys compare as decoded values under the receiving key contract, so different escape or numeric spellings cannot evade uniqueness. String and Char remain distinct, and Bool is not a numeric key. Record labels remain identifiers, while map keys are data: a string-keyed map does not become a record.

The empty forms never change kind:

  • {=} is always an empty map and {} is always an empty collection.
  • A map schema rejects {} and a collection schema rejects {=}. Schema context never changes a container's kind.
scores = {"Priya" = 10, "Rob" = 12},
empty_scores = {=},
empty_items = {},
empty_record = (),

Strings and characters

Strings use double quotes and Char uses single quotes. A Char decodes as exactly one Unicode scalar value. String contents are preserved without Unicode normalisation or implicit line-ending conversion. An unescaped newline or CRLF inside a string stays byte-for-byte content, because MON is data, not Moth source.

MON strings accept exactly \\, \", \n, \r, \t and \u{H...}. MON characters accept exactly \\, \', \n, \r, \t and \u{H...}. The Unicode braces hold 1 to 6 ASCII hex digits and accept either case on input; writer output uses uppercase hex. Empty braces, more than six digits, non-hex digits, surrogate values and out-of-range scalars fail. \0, \xNN, fixed-width \uXXXX, an escaped physical newline and every other unknown escape fail.

Templates are producer syntax only and are not accepted string literals in MON. A folded const template and an evaluated runtime template are each an ordinary String that a producer quotes; an unevaluated template is not a serialisable value. Compile time versus runtime concerns the producer and never changes document validity.

Numeric data

A numeric literal keeps its lossless spelling until the destination is known. Whole-number spelling and decimal/exponent spelling remain distinguishable, and numbers are never routed through f64 or display formatting.

The lexical rules are strict. Exponents use lowercase e; uppercase E fails. Unary + fails, and - is accepted only when attached to the literal. _ is allowed only between decimal digits inside the integer, fraction or exponent runs. Malformed, edge and double separators fail, and NaN and infinity have no MON spelling.

Conversion is strict about categories:

  • Int and exact Integer require whole-number spelling. Decimal data such as 3.0 fails an Int target even when mathematically integral, and 1e3 fails it too. Formatting cannot rewrite one category as the other.
  • Exact Decimal with a declared scale from 0 to 18 accepts whole, decimal and exponent forms only when the value is exact after removing trailing fractional zeroes and the effective scale is at most the declared scale. A scale-two target accepts 1.2 but rejects 1.239 without rounding.
  • Float accepts all valid finite categories and rejects non-finite source values and conversion results. Encoding round-trips the supported Float value including signed zero: negative zero writes -0.0 and positive zero writes 0.

Large integer and exact decimal data are retained and round-tripped without a second arithmetic runtime. Unsupported concrete adapters fail explicitly rather than narrowing or converting through Float.

Structs and choices

Both nested record forms are accepted:

size = (width = 1280, height = 720),
size = Size(width = 1280, height = 720),

These are alternative examples, not duplicate fields in one document. Anonymous records use named entries. A qualified nominal record literal follows the shared constructor argument rules without invoking user code.

A qualifier is one identifier: Unicode alphabetic or underscore start, Unicode alphanumeric or underscore continuation, case-sensitive. Dotted paths, aliases, registry lookup and whitespace-separated :: are invalid. The receiving schema determines the expected nominal type. An explicit qualifier is an additional checked assertion, never ignored and never used to select another schema. Matching payload shapes do not make unrelated nominal types interchangeable.

Choice data uses Moth-shaped variants rather than an invented tagged-record mapping:

widgets = {
    ::Text("Gold"),
    Widget::Progress(value = 0.4),
    ::Ready,
},

A unit variant has no parentheses and a payload variant requires them. ::Text(...) uses the expected choice from the receiving schema, while an explicit Widget qualifier must name that same expected choice. An unknown or mismatching explicit name fails.

Positional arguments precede named arguments. Target slots are routed once, every required slot is supplied exactly once, and unknown variants, duplicate payload fields, wrong arity and payload type mismatches fail. Choice payload fields have no defaults. Typed encoding checks any supplied qualifier before omitting it, and prefers unqualified named records with named choice payloads.

Schemas, defaults and options

Schemas define ordinary data shapes, field types, nominal identities, choice variants and explicit default values. They do not define a second expression language. Records are closed: every unknown field fails, including a misspelling of a field whose correct name has a default. Maps provide the explicit dynamic-key surface.

V1 supplies a small immutable Rust schema description for host callers. The engine defines its save-data contract once and supplies it explicitly. A prepared schema and its defaults are validated when prepared, before any document is processed, and the immutable prepared schema is reused across calls. Schema misuse is a structured failure, not a panic. There are no schema files, remote schema loading, runtime schema editing, registries or predicate DSLs.

Eligibility is derived transitively from the complete concrete schema. Every field, element, map entry and variant payload must have a supported mapping, and an unsupported member makes the enclosing shape ineligible even when the current instance does not use it. Functions, wires, routes, closures, live handles, unresolved resource pieces and deferred computations have no ordinary data encoding. A completed runtime-generated String is eligible. No mandatory serialisation trait, per-type marker, rename or skip attribute, custom codec hook or constructor execution participates in decoding.

Optionality permits none. Only an explicit field default permits omission. A missing optional field without a default is an error. Missing fields, explicit none and empty values remain distinct.

Defaults are prevalidated data, not runtime factories. A default applies only at the exact missing field. A supplied none is validated as none and never replaced by a default. A supplied nested record is validated as that record, not deep-merged with the parent's default record.

For a parent field layout with no default, omission fails even when every field inside the Layout schema has a default. Supplying layout = () permits those inner defaults to apply. If layout itself has a default, omission uses that complete value. () remains an empty record at the format level; it becomes a completed default-valued record only when its receiving schema permits every omission.

Normal typed encoding emits all completed fields, including explicit none and values equal to defaults.

Trees, not graphs

The data format represents value trees. Repeated shared source values are encoded at each occurrence, and decoding establishes no preserved alias relationship or allocation identity. Public Value is an owned tree, so cyclic host data cannot be represented by this API. Public SchemaType values form finite owned schema trees rather than named schema references. Each schema describes only its explicit nesting levels, and the codec validates values against those levels and the receiver's limits. Applications can encode graph links as ordinary identifiers and reconstruct them explicitly.

Limits and first errors

The codec consumes complete documents and fails fast. Incremental input, streams and multiple-document framing remain deferred. Finite configurable budgets bound input bytes, nesting, node counts (including one additional node for each map entry), numeric digits, default expansions, decoded bytes and encoded output bytes. The default depth budget is 64; Limits::MAX_SAFE_DEPTH sets a hard ceiling of 64 for configurable max_depth, and schema preparation rejects larger policies. Each counter is checked before the affected allocation or expansion, including default expansion and repeated shared-value expansion. The other defaults are 1 MiB of input, 100,000 nodes, 4,096 numeric digits, 16 MiB of decoded bytes, 16 MiB of output bytes and 10,000 default expansions.

Limits are receiver resource policy, not grammar dialects. A valid document may exceed a receiver's budget, and that outcome is reported distinctly from syntax and schema errors.

Both operations publish only complete successful results. On failure, partial values and output buffers are discarded and no partial public result exists. Each failure is a structured first error with a stable reason and a field or element path where available; decode errors include the original input byte range when available. Messages are rendered only at the caller's diagnostic boundary.

Deterministic writing

Typed record fields write in schema declaration order. Collection and map order is preserved. Public encode_document and encode_value emit compact output; pretty formatting is private to writer tests and has no public mode. Given the same ordered value, schema and encoder version, output is deterministic, with no promise that all semantically equivalent documents share identical bytes.

Formatting authored text is distinct from typed encoding. It cannot silently fill omitted fields, reorder maps, remove unchecked qualifiers or erase numeric categories.

Resources and versions

MON carries resource identifiers as ordinary strings. Compiler structural resource pieces are resolved to their final characters before encoding, and an unresolved value fails conversion to concrete MON data. V1 performs no path discovery, URL generation, filesystem checks or resource loading, and no string scan reconstructs dependencies.

The receiver supplies the schema. There is no mandatory schema header, reserved universal version field or automatic schema discovery. Applications may declare an ordinary format_version field with explicit migrations. Closed schemas never silently fall back to another version or repair mismatches.

Deferred source and builder surfaces

MON text has no file IO, module imports, schema discovery, command, builder registration, output write or runtime opcode. Compiler $mon convenience, with its invocation syntax still undecided, belongs to later Moth-native integration, as do Moth-side encode and decode operations, automatic schema extraction from ordinary Moth types and the static .mon project builder.

MON's local escape decoder adds no source-language syntax. The {=} empty-map distinction, Unicode escapes and contextual ::Variant construction remain deferred source parity unless another authorised syntax change has already delivered them.
