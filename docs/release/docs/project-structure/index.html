Documentation / Project structure

Project structure

A Moth project combines directory-scoped modules, one strict project config and a builder that selects the final artefacts.

Normal module roots start with @. Support and package-facade roots start with +. The rest of the filename stays cosmetic. export: currently defines the public API. $page will declare HTML artefacts; today the builder still selects entries from implemented root activity.

Project layout

Current versus accepted. Alpha scaffolds still use grouped config and reserved page metadata. The accepted $config/$project/$html_builder and root-only $page forms are queued. moth new doesn't emit them yet.

A Moth project has one config file, one source root and generated output folders.

Accepted starter config

$config
version #String = "0.1.0"

$project(
    name = "my_site",
    version = version,
    entry_root = "src",
)

$html_builder

Where things live

  • config.moth at the project root controls build settings.
  • src/ (or whatever entry_root says) holds your source files.
  • dev/ and release/ are generated output. Do not edit them.

One root file per module directory

Each source directory can have one root file. An @*.moth root creates a normal module. The text after @ stays cosmetic, so @page.moth, @api.moth and @mod.moth all create the same root role. A root becomes an HTML artefact only when it declares a root-only page:

$page

The current scaffold's src/@page.moth filename doesn't mean it already has this accepted page syntax.

Shared scoped packages

A +*.moth root creates a scoped support package instead of a normal module. For example, shared/+package.moth creates @shared. Its owner module, normal sibling modules and their descendants may depend on it. Other support packages in the same scope and the package's private implementation subtree cannot. A directory cannot contain both @*.moth and +*.moth roots.

The current scaffold creates an empty legacy lib/ folder. It has no special meaning in the accepted package design.

Outputs are generated

The build command creates output folders. They are not source. The builder cleans up stale artefacts automatically.

Current support versus accepted design. The Alpha compiler still uses grouped project and html records, direct #Config fields and reserved page_* metadata. The accepted $config, $project, $html_builder and root-only $page forms are queued, and moth new does not emit them yet.

A Moth project is a directory tree with one strict config file, a source entry root and generated output folders.

Accepted starter shape

The accepted starter keeps the version as an explicit configuration input and passes it to the required project field:

$config
version #String = "0.1.0"

$project(
    name = "my_site",
    version = version,
    entry_root = "src",
)

$html_builder

This is accepted queued design, not a claim about the current moth new scaffold. Keep operational projects on their current grouped config until the implementation cutover.

Project root contents

project-root/
├── config.moth
├── src/
│   ├── @site.moth
│   ├── shared/
│   │   └── +package.moth
│   └── pages/
│       └── @pages.moth
├── dev/
│   └── .moth_manifest
├── release/
│   └── .moth_manifest
└── .gitignore

Directory roles

  • config.moth is the only project config file. It lives at the project root and is not module source.
  • The configured entry_root (usually src) is the source folder the compiler searches for module roots.
  • dev/ and release/ are builder output folders, not source folders. They are generated and managed by the build system.
  • .moth_manifest files are build-system metadata used for safe stale-output cleanup. They are not source.

Structural packages

Project-local source-backed packages are structural +*.moth support packages. A +*.moth file in a source directory marks that directory as a scoped support package root named by its containing directory.

In the example above, shared/+package.moth creates the scoped @shared support package. It is visible to its owner normal module, normal sibling modules and their descendants. It is not dependency-bound from its own private implementation subtree or from another support package in the same scope.

No folder gains package meaning without a +*.moth root. Ordinary directories do not automatically become packages.

The optional project-root +*.moth facade beside config.moth is a separate mechanism for assembling public descendant surfaces for external consumers. It is not a scoped support package.

For the full package contract see Project-local packages.

Normal module-root files inside source directories

A non-config file whose name starts with @ and ends with .moth is a module root. The filename after @ has no language-level semantic role. @page.moth, @mod.moth, @api.moth and @anything.moth are equivalent root filenames.

The current moth new html scaffold may use src/@page.moth as a conventional root filename. That convention does not make the filename a page. In the accepted design, the root file declares an HTML artefact with a root-only $page directive:

$page

Helpers in ordinary files stay inside the surrounding module and cannot become entries on their own.

Current scaffold notice

The current scaffold creates current-syntax config.moth, a conventional src/@page.moth root and a .gitignore. It does not yet emit the accepted starter $config/$project/$html_builder shape or a live $page declaration. Do not infer implementation support from this teaching example.

Source versus output

Developers own source directories. The builder generates output folders and owns their stale-output cleanup. Treat generated artefacts as output, not source.

Builder-neutral frontend versus builder-owned output

The compiler frontend discovers modules, resolves dependencies, checks types, lowers code and validates borrowing. A project builder then decides how compiled modules become real output files. The current user-facing builder is the HTML project builder.

This separation lets the same frontend feed other builders. The frontend does not decide which modules produce artefacts. The builder owns that decision.

Only config.moth has config semantics

No other filename has config meaning. @config.moth is a module root, not a config file. Alternate config filenames, compatibility handling and config-specific diagnostics for other names are not supported.

Project config

Current support versus accepted design. Today config.moth still uses grouped project and html records. $project, $html_builder and a required version argument are accepted queued design. moth new does not yet emit them. See Progress.

config.moth at the project root controls build settings. It is one self-contained compile-time source file with no source dependencies.

Accepted starter

Module roots

Current versus accepted. The Alpha builder still finds HTML entries from root activity. The accepted design uses a root-only $page declaration. Current export: blocks are implemented; later $export migration remains deferred.

Each source directory can contain one module root. A normal module uses an @*.moth root, while an API-only support package uses a +*.moth root.

One root per folder

The filename after @ or + does not matter. @page.moth, @mod.moth and @api.moth all create the same normal-root role. One directory cannot contain two roots or mix an @*.moth root with a +*.moth root.

Bind the module, not the root file

Normal module-root files have no direct dependency form. Bind the directory's public module surface.

The @ in @page.moth marks the file as a module root on disk. The @ in @pages starts a dependency path. They share the same symbol but are not combined. Do not write @@pages. The second @ is invalid.

@pages

Root and helper roles

The root file defines the module identity. Files without @ remain helpers in that module. Helpers cannot become entries or pages on their own.

After the accepted page cutover, an HTML artefact needs an explicit root purpose:

$page

export: currently controls public declarations. The later $export spelling will replace it; both forms won't remain permanent alternatives.

Current support versus accepted design. Alpha projects still select HTML entries from implemented root activity. The accepted queued page design makes $page the explicit artefact declaration. Current export: blocks remain implemented; the later $export migration is deferred.

A normal module root defines the identity of one directory-scoped module. It does not define a page merely because its filename contains page.

Root filename semantics

A non-config file whose name starts with @ and ends with .moth is the module root for its containing directory. The filename after @ has no language-level semantic role:

@page.moth
@mod.moth
@api.moth
@anything.moth

The compiler treats each spelling as the root for its directory. The HTML route comes from the directory position, not from the root filename. After the page cutover, a root declares an HTML artefact only with a root-only $page directive.

One root per directory

A source directory may contain at most one non-config @*.moth file. Two or more normal module-root files in one directory are rejected with MOTH-CONFIG-0001. The explicitly selected synthetic single-file root forms its own module and follows the single-file page rule.

Config files are not module roots

config.moth is the project config file. It is not a module root, does not produce HIR and does not export declarations. @config.moth is a module root, not a config file. Only plain config.moth without @ has config semantics.

Direct root-file dependencies are rejected

Normal module-root files have no direct dependency form. Bind the directory's public module surface.

The @ in @page.moth is a filesystem marker identifying a normal module root. The @ in @pages is the source syntax that introduces a dependency path. These use the same symbol to visually connect module roots and dependency roots, but they are not concatenated. The module's dependency identity comes from its directory or registered package name. The cosmetic root filename is never a dependency name.

Given this structure:

src/
├── @site.moth
└── pages/
    ├── @page.moth
    └── article.moth

Valid:

@pages

Invalid:

@@pages
@@page

Neither @page.moth nor @site.moth is bound directly. Do not add the root file's leading @ to a dependency path.

Normal files belong to the surrounding module

Files without @ in the same directory as a root are normal source files within that module. They contribute declarations that the module root can bind and export. They do not execute top-level runtime code independently, and they cannot become page entries by themselves.

Root identity, page purpose and activation

Every selected normal module is compiled into an immutable module artefact. Its top-level runtime work becomes a dormant compiler-synthesised start. The current builder selects entries from authored runtime or fragment activity. The accepted design instead requires an authored root purpose, initially $page, before the builder selects an HTML artefact.

$page

Helpers remain declarations inside the surrounding module. They never own an entry, an independent start or a page. Binding a module exposes only its public interface and never activates its root work. A selected page root activates its module-owned start once and assembles its direct fragments in source order.

Visibility status

export: is the implemented public-API block. It controls which legal root declarations and direct selections cross a module boundary. The accepted future $export migration will replace this spelling rather than leave both forms as permanent alternatives. Whether a future export directive supports a block remains undecided. Do not use $export as current syntax.

Migrating older module projects

  • Rename the project config file to plain config.moth.
  • Keep one non-config @*.moth root per source directory. Merge old @page.moth and @mod.moth roles when they shared a directory.
  • Keep current export: blocks until the later $export migration is implemented.
  • Bind the module directory or package prefix. Do not bind the normal module-root filename directly.

Public API

Current versus future. export: is the implemented public API marker. The later $export migration will replace it. Its directive-block syntax is undecided, and the two forms won't remain permanent alternatives.

Declarations are private to their module by default. The export: block marks what other modules can see.

A compact export block

private_helper || -> String:
    return "private"
;

export:
    public_name #= "Moth"

    render || -> String:
        return private_helper()
    ;
;

Private by default

Files in the same module can see each other's declarations. Other modules can only see what the root's export: block makes public. The # marker means compile-time constant, not public visibility.

Re-export direct selections inside the same current block. Don't use $export until its migration and syntax land.

Current support versus accepted design. export: is implemented and remains the only public API marker in current source. The accepted future $export migration will replace it later. Directive-block support for that migration is undecided, so these forms will not remain permanent alternatives.

The current export: block is valid only in a module root file. It marks legal declarations as visible to other modules.

Syntax

private_helper || -> String:
    return "private"
;

export:
    public_name #= "Moth"

    render || -> String:
        return private_helper()
    ;
;

Rules

  • export: is valid only in a module root file. An export: block in a normal source file is rejected with MOTH-RULE-0077.
  • A module root may contain at most one export: block. Duplicate blocks are rejected with MOTH-RULE-0085.
  • The block ends with normal Moth ;.
  • An empty export: block is rejected with MOTH-RULE-0080.
  • Items inside the block are ordinary top-level module-root items marked public.
  • Items outside the block remain private to the module.

Allowed inside export:

  • direct-selection source clauses (re-exports)
  • direct-selection external clauses
  • functions
  • structs
  • choices
  • type aliases
  • traits
  • compile-time constants using #

Rejected inside export:

  • runtime bindings
  • mutable bindings
  • top-level executable statements
  • runtime templates
  • top-level const page fragments
  • trait conformances
  • trait incompatibility declarations
  • receiver methods as directly exported symbols
  • bare namespace dependency bindings or exports
  • wildcard exports
  • export lists
  • function alias exports
  • nested export: blocks
  • all legacy inline export forms

Runtime statements inside the block are rejected with MOTH-RULE-0080. Legacy inline export syntax without the : block delimiter is rejected with MOTH-SYNTAX-0001.

Re-exports

The export block can re-export direct selections from other files:

export:
    @components/card CardData as Card, render_card

    @core/math PI, sin
;

The selected alias becomes the public name. In this example cross-module consumers can depend on Card, not CardData, unless the export block lists CardData separately.

# constants are compile-time, not visibility

The # marker on a binding means compile-time constant. It does not control cross-module visibility. Cross-module visibility is controlled exclusively by the export: block.

Same-module versus cross-module visibility

  • Normal declarations in any file within a module are visible to other files in the same module by default.
  • Cross-module dependencies can only access declarations marked public by the module root's export: block.
  • Private declarations in the module root file are not available to other modules.
  • A module root with no export: block exports nothing.

Future migration

The accepted $export direction belongs to the general directive family, but its exact block syntax and migration timing remain future work. Recognition or documentation of its name does not add semantics. Do not write $export in a current project, and do not promise that both spellings will be supported forever.

Choose the explanation level: Active-root runtime and fragments

Active-root runtime and fragments

Current versus accepted. Alpha HTML entries still come from root activity. The accepted design requires a root purpose, initially $page. Dependencies never activate their roots.

Root activation

Top-level runtime code in a selected module root becomes a dormant start. It runs once when that module becomes a page entry. Helper files provide declarations and never own an entry or an independent start.

Purpose and comments

An unmarked root with authored runtime work or direct output needs a purpose, even inside if false. API-only declarations need no purpose. Semantically classified $doc, $note and $todo templates count as documentation and don't need one.

An accepted page can contain metadata alone:

$page

It still emits a complete document. A dependency cannot make unpurposed runtime work legal by keeping it dormant.

Page fragments

Direct top-level templates in the selected root remain fragments:

  • A const fragment (the # prefix form) becomes static HTML.
  • A runtime fragment (the plain bracket form) runs through the root's start.

The builder keeps static and runtime fragments in source order. Assigned or returned templates are ordinary values, and helpers cannot create page fragments by themselves.

Current support versus accepted design. The Alpha builder still treats authored runtime work and fragments as HTML entry activity. The accepted queued design requires an explicit root purpose. Initially, only root-only $page supplies the HTML purpose. Dependency roots remain non-activating in both designs.

Every selected normal module is compiled into an immutable module artefact. Its top-level runtime work becomes a dormant compiler-synthesised start. Entry assembly activates that module-owned start exactly once for a selected page. A dependency exposes declarations without activating its root.

Explicit root purpose

Top-level executable work or direct output requires a recognised purpose with an applicable consumer. $page is the initial and only HTML purpose in the accepted design:

$page

The purpose applies to the whole normal root rather than to statements after the directive. A root with only functions, types, constants or other API declarations remains valid without a page. An unmarked root with authored runtime work, direct output or fragments still needs a purpose even when an optimisation could prove the work unreachable. A static if false, an empty direct fragment and an immutable runtime binding do not erase the authored role.

Future $test may provide a non-page purpose for a separate testing consumer. It is deferred and cannot make a root valid today. A metadata directive also cannot authorise runtime work merely because it appears in the file.

Comment and documentation exemptions

Semantically classified $doc, $note and $todo templates are documentation/comment processing. They do not need a root purpose and do not create an HTML entry by themselves. This exemption follows the template's semantic category, not whether its rendered output happens to be empty.

Assigned or returned template values are ordinary values, not direct output. Their containing runtime code follows the normal purpose rule.

Entry-activated root runtime

The selected module root's top-level runtime code becomes a dormant compiler-synthesised start function. Entry assembly activates it exactly once. This includes top-level bindings, function calls and other runtime statements. Helper files define reusable declarations. They do not own an export block, an independent start or an entry.

Page fragments

Two forms of direct top-level template in a module root become page fragments:

  • A const fragment uses the # prefix before the opening bracket. It folds at compile time and is emitted as static HTML.
  • A runtime fragment uses the plain bracket form without #. It is evaluated by the module's start function when entry assembly activates it and inserted into the page at runtime.

The builder preserves source order between static and runtime fragments. Static fragments are emitted immediately. Runtime fragments use generated slots in the HTML document, then the embedded JavaScript calls the module start function and fills those slots.

Metadata-only pages

A root with only $page metadata still emits a complete page with default document metadata. A page containing only resource-bearing metadata also emits the complete document and the resources it uses. It does not need non-empty executable HIR, an artificial fragment or generated runtime code.

Dependency roots

Dependency module roots never activate their root runtime. When a module is bound for its public API, its top-level runtime code, start body and page fragments remain dormant. Only exported declarations remain available.

The purpose policy still applies when a root is compiled as a provider. A consumer cannot make invalid unpurposed runtime work legal by keeping it dormant. Valid dependency access and check remain non-activating, but neither operation suppresses a purpose diagnostic.

Do not put page fragments in helper files

Helper files should define reusable declarations. The module root should bind and use them. Page-producing top-level templates belong in the selected module root only. An ordinary file cannot become a page by containing a fragment.

Choose the explanation level: HTML routing and artefacts

HTML routing and artefacts

Current versus accepted. Alpha emits HTML from root activity and expects a homepage at the entry root. The accepted design keeps directory routes but requires explicit root-only $page pages and command-specific no-page rules.

Directory routes

Routes come from directory position, not from the @ filename:

src/@page.moth       -> index.html
src/about/@module.moth -> about/index.html

The root filename is cosmetic. An ordinary file and index.moth have no page meaning.

Page and command rules

After the cutover, a normal root needs an explicit page purpose:

$page

check accepts a valid zero-page project but still rejects unpurposed runtime work. HTML build and dev need a page somewhere below entry_root, not necessarily at its root. Single-file HTML output requires $page on its synthetic root. A metadata-only page still emits a complete document.

The builder does not invent a homepage or scan arbitrary .moth files. Generated dev/ and release/ folders remain output, not source.

Current support versus accepted design. The Alpha HTML builder currently emits routes for roots with authored runtime work or fragments and expects an artefact at the entry root. The accepted queued page design selects only roots with an explicit $page purpose. It keeps directory routes and replaces activity-based emission and the mandatory homepage with command-specific no-page rules.

Directory-based routes

The module root's directory determines the HTML output path:

src/@page.moth              -> index.html
src/docs/@page.moth         -> docs/index.html
src/docs/basics/@module.moth -> docs/basics/index.html
src/@home.moth              -> index.html
src/@api.moth               -> index.html

The root module maps to the project index when it declares a page. A nested directory maps to a nested index route. The normal module-root filename (@page.moth, @home.moth, @api.moth) has no effect on the route name.

An ordinary file cannot declare a page, and index.moth has no special meaning. The page migration adds no route override, filename-derived route, page alias or new redirect. Existing page_url_style and redirect_index_html policies stay unchanged.

Explicit pages

After the accepted cutover, a normal module root becomes an HTML artefact only when it declares the root-only $page purpose:

$page

The root at entry_root may remain declaration-only while descendant roots declare pages. Each page candidate comes from the existing normal-module root inventory; the builder does not scan arbitrary .moth files. A metadata-only page and a page whose metadata uses resources both produce a complete document.

Command-specific no-page rules

The accepted command policy distinguishes checking from HTML output:

  • Directory-project check accepts a valid project with zero pages. It still rejects authored runtime or direct output without a purpose.
  • HTML application build and dev require at least one page anywhere below entry_root. They do not require a homepage at entry_root.
  • Single-file check accepts a declaration-only synthetic root, but authored runtime or output still needs a purpose.
  • Single-file HTML output requires $page on the explicitly selected synthetic root.

Do not fabricate index.html to satisfy development tooling. Serve descendant routes normally. If a tool needs a launch page, choose the real homepage when present or the lexicographically first normalised page route. That choice doesn't create a redirect or route alias. Requests to an absent site root retain ordinary missing-route behaviour.

Builder ownership

The HTML builder owns route and artefact policy. The frontend remains builder-neutral. The builder decides:

  • which $page roots produce HTML artefacts
  • how routes are derived
  • how output files are organised
  • whether to reject unsupported reachable features

Source stays target agnostic. The HTML builder may choose JavaScript, Wasm or mixed output, but source cannot query or branch on that choice. Builder packages expose stable capabilities rather than target identity.

Output folders

The builder generates output folders and manages them through manifests. Builder settings in config.moth own output paths. HTML defaults to dev for development and release for release builds. Treat generated folders as build artefacts, not source.

Release versus development output

The default build writes to the dev folder. The --release flag writes to the release output folder. The dev server serves from the dev folder.

Experimental Wasm mode

In the experimental --html-wasm mode, the builder can emit a route folder containing index.html, page.js and page.wasm instead of a single HTML file with embedded JavaScript.

Build configuration values

Build configuration values let a project or source module receive typed primitive values before its modules are compiled.

Current support versus accepted design. Direct and source #Config and typed --input values are supported. $config prefixes and explicit-only providers are accepted queued design. See Progress.

Accepted $config

$config
analytics #Bool = false

if analytics:
    send_analytics()
;

The name is the input name, the type is the contract and = is the fallback. A required non-optional input may omit the initializer. Ordinary constants still need one.

Only $config declarations create contracts. A $project field named version does not supply a source input named version.

Current #Config

analytics #Config of Bool = false

Command examples

moth build . --input enabled=true
moth build . --input retries=4
moth build . --input api_url=https://example.com

Bare true and false infer as Bool, whole numbers as Int, decimal values as Float, and other text falls back to String. Quote "true" when a String is intended.

Build configuration cannot inspect operating-system, architecture, backend or target identity.

Current support versus accepted design. Direct and source #Config of T contracts, typed --input values, ordinary static if and explicit @project are implemented. $config prefixes and explicit-only providers are accepted queued design. See Progress.

Build configuration values are typed primitive values resolved before module AST execution semantics are finalised. They can represent schema-approved settings and similar stable semantic configuration. They do not represent project identity, source-discovery settings, operating-system, architecture, backend or target identity.

Use the validated fallback

Optional type with no initializer or = none

Resolve to absence

Optional type with a present initializer

Use that present fallback

Ordinary constants still require initializers. Only a marked configuration contract may omit one. Reject inferred #= configuration contracts, runtime or mutable bindings, multi-bind targets, parameters, fields, function-local declarations and type-position or value-position directives.

Accepted types stay String, Int, Float, Bool, Char and one optional layer around those primitives.

Explicit-only providers

Only $config declarations create input contracts.

  • $project(version = "1.0") is project metadata, not a version input provider.
  • An ordinary version #String = "1.0" is a helper constant, not an input provider.
  • Passing release_version to $project(version = release_version) does not rename its input contract.
  • @project publishes only predefined project fields.

Matching declarations within one compilation boundary agree on name, primitive type, optionality, required or default state and normalised default value. Each project or package boundary owns its own namespace.

Bootstrap versus source defaults

In config.moth, a fallback may use earlier visible helper values on the allowed single-file compile-time surface. Same-file forward references remain errors.

In source modules, defaults remain self-contained primitive literals or none. Names, projections, expressions, templates, calls, casts, collections, records and references to other configuration values remain invalid defaults.

Bootstrap contracts resolve from explicit input, a compatible builder primitive global, the fallback or a required-input diagnostic. Source contracts resolve from a matching bootstrap contract, explicit source-only input, a compatible builder global, the common source fallback or a required-input diagnostic.

Current #Config spelling

Until the cutover, operational source still uses:

api_url #Config of String = "https://api.example.com"
max_retries #Config of Int = 3
analytics #Config of Bool = false

Direct project #Config fields remain the current project-input path. They are not the accepted end-state provider model.

Command build-input typing

The command accepts repeated --input name=value arguments. It splits at the first = and preserves all later = characters. Names must be lower_snake_case. Values are typed immediately in this order:

  1. exact lowercase true or false -> Bool
  2. a complete valid signed whole-number literal -> Int
  3. a complete valid decimal-point or exponent literal -> Float
  4. a complete valid single-quoted character literal -> Char
  5. a complete valid double-quoted string literal -> String
  6. every other value -> String

Examples:

moth build . --input analytics=true
moth build . --input retries=4
moth build . --input ratio=0.75
moth build . --input api_url=https://example.com
moth build . --input 'label="true"'
moth build . --input "separator=':'"

Anything else, including empty text after name=, falls back to String. A value beginning with a quote must be a complete valid quoted literal; malformed quoted text is a command-input diagnostic rather than a String fallback. Bare none is String text. To force an ambiguous String such as true or 42, use explicit double-quoted Moth String syntax. A Char requires explicit single-quoted syntax and never infers from an unquoted character.

Omitting an input lets optional absence resolve to none through the contract or default. A concrete T input may satisfy a matching T? contract as a present value. There is no implicit numeric/String coercion: in particular, Int does not satisfy Float. Programmatic build APIs use the same typed carrier and conversion policy.

Ordinary static if

Ordinary if is the only conditional source form. There is no $config if and no #Config if.

$config
analytics #Bool = false

if analytics:
    send_analytics()
;

Both branches remain valid Moth source and complete frontend validation, including unknown directives. A known Bool selects the executable branch before HIR. This does not condition imports, declarations, exports or package topology. Future $feature is a separate pre-graph structural-selection contract.

Platform boundary

Moth source cannot inspect or branch on operating system, architecture, backend, target or runtime-platform identity. Builders own physical target decisions and map stable source semantics and capabilities to JavaScript, Wasm or other platform-specific artefacts.

Entry metadata and page directives

Current support versus accepted design. @project is implemented. $page is accepted queued design. Pages today still use reserved page_title and related names. See Progress.

Using @project

Bind @project to read predefined project fields:

@project version

footer #= [: v[version]]

@project is never implicitly injected.

Root-only $page

$page will be legal only on a normal module root, or on an explicitly selected synthetic single-file root. Helper files cannot declare pages.

$page(title = "About")

Bare $page uses defaults. $page() is invalid. Title, description, language, favicon, body style and head content are optional compile-time arguments.

$page is the initial document metadata. Runtime io.set_title is a later capability-checked call, not a rewrite of that metadata.

HTML build and dev need a page somewhere under entry_root. check can accept a valid project with no page. Future $test is a later non-page purpose.

@project

@project is an explicitly bound immutable namespace. The accepted $project directive publishes its predefined fields only. Today's grouped record also publishes supported extra metadata until that configuration cutover.

@project version

footer #= [: v[version]]

$page

$page is accepted queued HTML-builder metadata and the first planned root purpose. Bare $page uses the declared defaults. $page() is invalid.

$page(
    title = "Moth",
    description = "A language for creating reliable software",
    lang = "en",
    favicon = @assets/favicon.svg,
)

The positional parameter order is title, description, lang, favicon, body_style, head. All six accept compile-time String? values, including structural resource-bearing Strings, and default to none.

Placement:

  • top level of a normal module root, at most once
  • the explicitly selected synthetic single-file root, at most once
  • invalid in helper files, support roots, facades, config.moth, bodies, export: and a second $page in the same root

$page describes the whole root. Same-file forward references in its arguments remain invalid.

Initial document metadata

Every parameter is String? = none. none means no page override, including when supplied explicitly. A present empty String remains a present value where the existing metadata domain permits it.

  • A present title supplies the base title. Otherwise use the existing route-title fallback, then the project name. Apply the builder's initial title prefix and postfix to that base title.
  • An absent description emits no description element. Absent lang, favicon and body_style use the HTML builder's document defaults.
  • An absent head adds no markup. A present head is one folded String inserted as HTML with its meaningful whitespace preserved.

Escape title text and attribute values for their existing HTML contexts. head is deliberately authored HTML, not title text. Compose it through normal constant/template expressions. There are no typed head nodes, repeated-call merges, += metadata updates or last-write-wins behaviour.

These are specific document-shell fallbacks, not generic inheritance between project and page configuration. Keep the same shell policy for HTML-JS and the existing HTML-Wasm output path.

Metadata ownership and resources

Arguments use ordinary root-file compile-time visibility, including earlier same-file constants, dependency-bound constants, explicit @project members and resolved source configuration values. Same-file forward references remain invalid.

The module folds its own metadata once and stores owned non-HIR facts. Provider metadata never becomes consumer metadata, and entry activation never compiles it again. Resource and site-root anchors survive folding and remapping until output planning. Retain the authored argument spans on metadata resource uses.

A tracked favicon enters the ordinary graph and resource pipeline. Only uses reachable from selected metadata, fragments or code enter output unions. Builder resource handling never scans rendered HTML or HIR constant names. A metadata-only page can therefore emit its document and resources without artificial runtime work.

Runtime title mutation is a separate, queued Core IO capability. Its exact behaviour is defined in Core IO.


Explicit root purpose

Top-level executable work or direct output requires a recognised purpose with a consumer. Only $page works initially. Functions, types and constants without purpose remain a valid API-only root. Semantically classified $doc, $note or $todo templates do not require a purpose. Future $test is a later non-page purpose; it cannot satisfy validation until implemented.

Command policy

A declaration-only root at entry_root is valid. HTML application build and dev need a page somewhere below it, not necessarily a homepage at entry_root. check accepts valid zero-page projects and still rejects unpurposed runtime work. Single-file HTML output requires $page.

Current page metadata

Until the cutover, operational pages keep reserved names such as page_title and page_head. Do not add live $page statements merely because this page documents them.

Choose the explanation level: Project package facade

Project package facade

Accepted API-only boundary. The external project package facade remains partially implemented. It cannot become an application entry through generic directives.

A project can expose a public package API to other projects through an optional facade file at the project root.

What a facade does

A +*.moth file beside config.moth becomes the project package facade. It exports declarations that external consumers can bind. Without it, the project has no externally consumable package surface.

The facade rejects top-level runtime work and page fragments. It cannot declare root-only $page metadata, has no implicit start and emits no route. Support roots follow the same API-only rule.

How it reaches descendant modules

The facade can reference public interfaces of modules below entry_root even though ordinary module visibility wouldn't allow it. Stage 0 gives the facade a special assembly namespace for this purpose.

Privacy and inputs

It cannot depend on @project or expose declarations that depend on project-private context. Configuration input contracts stay scoped to one project or package boundary; a consumer doesn't satisfy a dependency's contracts implicitly.

Current support versus accepted design. Source-package and module foundations are partially implemented. The complete external facade and project-context contract remains partial. This page defines the accepted final contract. The facade is API-only: no generic directive can turn it into an application entry.

The project package facade exposes a project's public API to external consumers. It is compiled through the ordinary compiler pipeline with project-facade visibility supplied by Stage 0.

The facade root

One optional project-root +*.moth file beside config.moth defines the external project package facade. The suffix after + is cosmetic.

The facade may define and export its own legal API-only declarations: functions, structs, choices, type aliases, traits and compile-time constants.

Special assembly namespace

Stage 0 gives the facade a special assembly namespace rooted at entry_root. Through that namespace it may reference the public interfaces of descendant modules below entry_root, regardless of ordinary lexical module visibility.

Facade restrictions

The facade:

  • never bypasses an export: boundary
  • isn't visible to internal project modules
  • cannot depend on @project
  • cannot expose a semantic fact that depends on project-private context
  • rejects top-level runtime work and page fragments
  • cannot declare root-only $page metadata
  • has no implicit start
  • emits no route or HTML artefact

Support roots and the project package facade reject top-level runtime work and page fragments. They don't merely stay inactive. Generic directives also cannot promote a facade or support root into an application entry. A future directive cannot weaken this API-only boundary without an explicit contract owned by the facade/package design.

Project package assembly

The compiler produces an immutable facade module artefact and public interface. ProjectPackageAssembly is a separate link plan over:

  • the compiled facade artefact
  • selected descendant public interfaces
  • reachable generated functions
  • package runtime requirements permitted by the target

Assembly never recompiles or mutates the facade.

A project may be both an application and a package. Without the facade it has no externally consumable Moth package surface.

The facade package identity comes from project.name.

External package eligibility

The build system rejects any declaration whose public semantic facts or reachable executable implementation directly or transitively depend on private @project. This includes an exported function that calls a private project-dependent helper.

The validator doesn't treat implementation-only dependence as a reusable package specialisation mechanism.

Dependency package facades

A dependency package exposes its facade and immutable artefacts to consumers. Consumers never see the dependency's private @project.

No declaration exposed through a dependency package facade may directly or transitively depend on that dependency's private @project. Private declarations may use the dependency's own @project only when no external package export can reach or expose them.

Configuration namespaces are scoped to one project or package compilation boundary. A consuming command's unqualified CLI or programmatic inputs don't implicitly satisfy a dependency's $config contracts.
