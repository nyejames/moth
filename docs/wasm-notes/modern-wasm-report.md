# Moth Wasm Backend Reference

## Scope and recommended target

For a compiler being built now, “modern Wasm” should mean the current core WebAssembly 3.0 editor’s draft as the main instruction and type reference, with the proposals repository used as the feature-status ledger, and the entity["organization","W3C","web standards consortium"] Candidate Standard track used to understand publication status. As of 30 April 2026, the editor’s draft identifies itself as WebAssembly 3.0, while the W3C publications are being maintained as living Candidate Standards with the latest Candidate Recommendation snapshot dated 17 December 2024. citeturn1view0turn42search5turn45view1

My recommendation is to split Moth’s Wasm plan into two tiers. The first tier should land with features that materially simplify lowering without forcing a full runtime redesign: multi-value, typed function references, extended constant expressions, multiple-memory-aware IR, selectable memory32 versus memory64, tail calls where legal, and optional exception handling and SIMD. The second tier should be designed for now but not required for the first backend: GC, threads and atomics, stack switching, wide arithmetic, custom page sizes, and component packaging. That split matches both the finished-proposal set already folded into the 3.0 draft and the active proposals still progressing through the process. citeturn44view0turn43view0turn24search0turn24search1turn24search2turn24search3

No Moth HIR documentation was available in this conversation. The HIR guidance below therefore assumes a typed, front-end-stable HIR with resolved names, explicit operator kinds, and no backend-specific storage assumptions. The important part is not the exact node taxonomy, but the invariants preserved when translating into LIR.

## What modern Wasm looks like in May 2026

Release 3.0 materially expands core Wasm relative to the 1.0 and 2.0 worldview. The current change history folds in extended constant expressions, tail calls, exception handling, multiple memories, 64-bit address spaces for memories and tables, typed or typeful references with `call_ref`, GC types and recursive subtyping, relaxed SIMD, profiles, and custom annotation syntax in the text format. The finished-proposals ledger also records tail calls, extended const, typed function references, GC, multiple memories, relaxed SIMD, branch hinting, exception handling, JS string builtins, and Memory64 as part of the 3.0 line. citeturn18view0turn18view1turn18view3turn20view0turn20view1turn20view2turn20view3turn22view1turn44view0

A practical consequence is that Moth’s backend should stop thinking in “MVP Wasm plus a few extras”. A 2026-capable backend has to be aware that block and function signatures are multi-value, calls may be direct, indirect, or by reference, memory and table address widths may be either 32-bit or 64-bit, and reference types now carry nullability and heap-type information. If the backend ignores those facts and hard-codes an MVP mental model, the resulting LIR will be awkward, lossy, and difficult to extend. citeturn44view0turn22view0turn20view1turn27view1turn25search0

Profiles are now part of the spec. The defined deterministic profile removes incidental non-determinism by forcing canonical positive NaNs and fixed behaviour for relaxed vector instructions, while the profiles appendix also says producers are expected to generate code for the full profile by default and should not make correctness depend on profile-specific execution. That is the right model for Moth too: treat deterministic execution as an explicit backend mode, not as the default semantics baked into the language IR. citeturn38view0turn37search2

If the output is meant for browsers, the JavaScript embedding draft is no longer a side concern. The current JS API draft is also a living Candidate Recommendation Draft, and it defines exact structural limits for modules accepted by the standard JavaScript embedding, including a 1 GiB maximum module size, 1,000 parameters to any function or block, 1,000 results for any function or block, and 50,000 locals per function. Those limits should influence Moth’s inliner, monomorphiser, block formation, and module-splitting strategy long before byte emission. citeturn45view1

## What the LIR should be

The core design choice is this: Moth’s LIR should be a Wasm-aware optimisation IR, not a literal stack-machine IR. Mature Wasm tooling points in the same direction. Binaryen keeps a main IR that is tree-shaped and optimisation-friendly, then uses an additional Stack IR for stack-machine-shaped optimisation and final code quality work. That is strong evidence that one IR should not be forced to serve both global optimisation and final stack-form emission equally well. citeturn40view0

A good Moth LIR should therefore be a typed CFG-plus-SSA IR with first-class block parameters, explicit terminators, and native tuple or multi-value support. That shape matches current Wasm better than phi-heavy or stack-only forms, because modern Wasm has multi-value functions and blocks, precise reference types, typed `call_ref`, multiple memories, memory64, tags, and GC type graphs. It also lets the backend preserve optimisation quality until a late stackification pass, instead of freezing stack order too early. citeturn44view0turn22view0turn20view1turn27view1turn30view1

In concrete terms, the LIR should make these properties explicit rather than implicit:

- **Exact value types.** Model scalar values as `i32`, `i64`, `f32`, `f64`, `v128`, or reference types with explicit nullability and heap type. Do not collapse references to “pointer-like”. `wasm-encoder`’s `ValType` and `RefType` APIs mirror this directly. citeturn25search0turn27view1
- **Address and container types.** Memory operations need an explicit memory index, while memory and table declarations need explicit `memory64` or `table64`, sharedness, and, for memories, optional custom page size. Those are not implementation details any more; they are part of the target-visible type system. citeturn20view1turn26view0turn27view0turn24search1
- **Feature requirements on nodes.** A `call_ref`, `throw`, `struct.new`, relaxed SIMD op, atomic op, or continuation op should carry the feature it requires. `wasm-encoder` already exposes instruction families spanning GC, exceptions, atomics, continuations, and even proposed wide-arithmetic operations, so the emitter can only stay sane if legality is decided above it. citeturn12view0turn10search1
- **Effect and trap structure.** Loads, stores, conversions, potential traps, allocation, host calls, atomics, and exception edges should be explicit in LIR. Wasm validation and execution rules care about these distinctions, and they matter for correct stackification and local placement. citeturn36search0turn18view3turn24search2
- **Late local allocation.** SSA values should be primary. Function locals are a late storage decision, especially because modern Wasm has non-defaultable reference types whose valid use depends on initialisation dominance. citeturn22view0turn40view0

The most future-proof version of this design is a two-layer backend model: one persistent LIR for analysis and optimisation, plus one derived “Wasm emission plan” that is structured, stackified, and local-allocated just before passing instructions into `wasm-encoder`. That extra layer is worth it.

## How Moth HIR should translate into that LIR

HIR-to-LIR should resolve every front-end ambiguity that would otherwise leak into instruction selection. That means overload resolution, signedness-sensitive comparisons and conversions, short-circuiting, match lowering, tail position, exception behaviour, and concrete ABI choices must all be fixed before the final Wasm pass. The final emitter should be selecting and ordering instructions, not still deciding language semantics. That separation matters more in Wasm than in many native backends because operand stack shape, block signatures, tag signatures, and reference exactness all depend on earlier semantic choices. citeturn18view1turn18view3turn22view0turn27view1

Expression-oriented HIR should lower into explicit basic blocks with typed block parameters and terminators. That is the cleanest way to map conditionals, loops, short-circuit boolean logic, and pattern-like control flow onto Wasm `block`, `loop`, `if`, `br_if`, and `br_table` structures later. Do not translate HIR directly into a stack of encoder calls. Translate HIR into explicit control flow first; only then structure and stackify it. Binaryen’s own split between its main IR and Stack IR exists for exactly this reason. citeturn40view0

Multiple return values should be represented natively in LIR, not faked through hidden out-pointers or synthetic tuple memory slots unless a specific ABI forces that. Multi-value is long since standardised, the 3.0 finished-proposals list still treats it as a core part of the modern language, and the JS embedding explicitly supports multiple values flowing through its host interface. If Moth’s HIR already has tuples or multiple result expressions, do not erase them during HIR-to-LIR. citeturn44view0turn45view1

Reference-bearing HIR should stay abstract enough to support both a linear-memory runtime and a future GC runtime. The current 3.0 core draft adds managed heap types, reference subtyping, struct and array types, recursive types, and cast or test operations. That is too much surface area to retrofit later if the first LIR hard-wires “all objects are integer addresses”. The better approach is to distinguish raw numeric addresses from language references in LIR now, even if the first Wasm backend lowers language references into a linear heap. citeturn20view2turn20view3

If Moth eventually wants async functions, generators, or green-thread-like semantics, the first backend should still lower them through explicit state-machine or runtime-assisted transformations in HIR or early LIR rather than depending on stack switching. Stack switching is active at phase 3, not standardised, even though `wasm-encoder` already has continuation-related instructions in its instruction model. That makes it a good future target and a bad initial dependency. citeturn43view0turn24search0turn10search1

## How LIR should lower to Wasm

Lowering from LIR to Wasm should be organised as a fixed sequence of backend passes, not a monolithic “emit Wasm” step. The sequence I would use is: target-feature selection, Wasm type and ABI materialisation, CFG structuring, stackification, local allocation and copy coalescing, section planning, then encoder emission. That order matches both the binary format’s strict section layout and the fact that some metadata, such as data counts and branch hints, can only be emitted correctly once layout facts are known. citeturn13view0turn36search0turn17view1

The structuring pass should turn CFG edges into Wasm nesting, preserving block signatures and branch values. Tail-position calls should be marked so the final pass can choose `return_call` or `return_call_indirect` when the feature is enabled and the call is legal. Exception-enabled code should become explicit tag declarations plus `try_table`, `throw`, and related control flow rather than pretending that exceptions are just host callbacks. Multiple memories and memory64 should already be solved at the LIR level, because memory and table instruction operand types depend on the declared address type of the subject memory or table. citeturn18view1turn18view3turn20view1turn31view0turn32view0

Section planning deserves its own backend data structure. The core binary grammar orders non-custom sections as type, import, function, table, memory, tag, global, export, start, element, optional data count, code, then data, and `wasm-encoder::Module::section` deliberately leaves correct ordering to the caller. A Moth backend should therefore build a section plan before emission, not append opportunistically. That same plan should know whether a data-count section is required; the core spec says it must be present if any data index appears in code, and the encoder exposes `DataCountSection` explicitly. citeturn36search0turn13view0turn35view0

One subtle but important pass is stackification. This is where SSA values become an evaluation order that minimises `local.set` and `local.get` churn while still preserving precise semantics. The pass should prefer stackable trees, keep multi-value edges intact where profitable, and spill only when duplication, control-flow joins, or validation constraints require it. This is the place to exploit Wasm-specific code-shape wins; it should not contaminate the main LIR. Binaryen’s separate Stack IR is a useful conceptual model here. citeturn40view0

Finally, if you expose a deterministic backend mode, implement it here as a legality and selection policy. In that mode, relaxed SIMD should either be avoided or mapped only where the deterministic profile still permits fixed behaviour, and floating-point operations should be treated with deterministic-profile expectations about NaN production. The spec’s profile design makes this a backend option, not a language redesign. citeturn38view0turn37search2

## How to use wasm-encoder effectively

The current `wasm-encoder` crate, in the entity["organization","Bytecode Alliance","open source foundation"] wasm-tools ecosystem, exposes `Module` as the central builder, section-specific encoders for the core binary format, optional `wasmparser` integration, and component-model APIs behind a feature flag. The crate root currently lists version 0.248.0 and complete documentation coverage. That is a good fit for Moth because the library is intentionally close to the Wasm binary model rather than trying to hide it behind a high-level IR. citeturn8view0

Use `TypeSection` and its single-use `CoreTypeEncoder` as the boundary between Moth’s type world and Wasm’s type section. The encoder can write plain function signatures as well as array, struct, subtype, continuation, and recursive type-group entries. If Moth’s runtime starts linear-memory-first, this still matters: the type path should be architected so GC and recursive types can be added without changing the emitter API shape later. citeturn11search0turn30view1turn29view0turn30view0

Use `Function` and `CodeSection` in two modes. For ordinary emission, create grouped locals with `Function::new`, write instructions through `instructions()` or `instruction()`, and append the body with `CodeSection::function`. For caching or incremental compilation, use `Function::into_raw_body` and later inject the saved bytes with `CodeSection::raw`; the docs explicitly call out this combination as suitable for caching code-generation results. That is valuable for a compiler like Moth, where repeated incremental builds are likely. citeturn10search0turn13view1turn14view0

Treat `InstructionSink` as the final mnemonic layer, not as the backend itself. Its API surface is instruction-shaped and very broad, covering scalar numeric ops, SIMD, atomics, GC instructions, tag and exception machinery, continuation instructions, and more. Once Moth’s late emission plan has made types, immediates, indices, offsets, alignments, and feature legality explicit, final emission should mostly be a mechanical walk that calls the corresponding sink methods. That is exactly where `wasm-encoder` is strongest. citeturn12view0turn41search1

Use the optional `wasmparser` integration aggressively in tests. The crate root example already validates emitted bytes with `wasmparser::validate`, and the `reencode::Reencode` API can parse whole modules, sections, function bodies, type groups, imports, exports, data, and tags while also providing a hook for interspersing or detecting sections. That makes it ideal for round-trip tests, differential tests, canonicalisation passes, fuzz minimisers, and “emit, parse, re-emit” sanity checks. citeturn8view0turn41search0

Emit auxiliary sections deliberately. `NameSection` helps debugging and has an ordering discipline for subsections; `ProducersSection` is a widely supported non-standard convention with recommended fields such as `language`, `processed-by`, and `sdk`; and `BranchHints` encodes the `metadata.code.branch_hint` custom section using byte offsets within function bodies. That last detail matters: branch-probability metadata in Moth should stay symbolic until the final instruction layout is known, then be translated into branch-hint offsets late. citeturn16view0turn17view0turn17view1

Keep component support out of the first core backend. `wasm-encoder` already includes `Component`, `ComponentBuilder`, canonical-function support, and other component-model types, but the proposals repository still lists Component Model at phase 1. The right architecture is to generate a strong core Wasm module first and keep the ABI boundary clean enough that a component wrapper can be added later as packaging rather than as the backend’s core responsibility. citeturn8view0turn43view0
